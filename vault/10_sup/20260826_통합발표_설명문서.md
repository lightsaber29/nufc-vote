# NUFC Fan Poll — 성능 개선과 규모 가정 검증

> **LCP 14.4s → 2.95s.** 정작 최적화하러 간 SQL은 77배 여유였고, 대신 틀린 값이 나왔다.

- 작성일: 2026-08-26
- 대상 서비스: NUFC Fan Poll (Newcastle United 팬 투표 플랫폼) · https://nufc-fan-poll.vercel.app
- 스택: Next.js 14 (App Router) · TypeScript · Supabase(Postgres/Auth/Storage/RLS) · Vercel · Mixpanel
- 독자: 캠프 심사 · 멘토
- 성격: **설명 문서.** 아래 모든 수치는 실측이며 출처를 각 절 끝에 표기한다. 근거를 못 찾은 항목은 「근거 미확인」으로 남긴다.

### 이 문서가 다루는 두 개의 작업

| | 질문 | 대상 |
|---|---|---|
| **①** 렌더링 · 캐싱 | 데이터를 **언제** 가져오는가 | Next.js 서버 컴포넌트 전환 + TTL 정책 |
| **②** 목표 규모 검증 | 데이터를 **얼마나** 가져오는가 | k6 부하 테스트 + 1,000행 캡 결함 |

①은 초기 화면 성능(Lighthouse), ②는 목표 규모에서의 동작 정확성(k6 + 화면 실측)을 다룬다. 두 작업은 인과로 이어진다 — ①이 만든 정적 생성·캐싱 구조는 **틀린 값도 똑같이 굳히기** 때문이다.

## 1. 문제 정의

### 1.1 사용자와 상황

- **사용자**: 뉴캐슬 유나이티드 팬(1차), SNS·커뮤니티 축구 팬덤(2차)
- **서비스 현황**: 투표 기능만 제공. 실사용 규모가 작고, 신규로 붙이는 승부예측 도메인은 **실사용 트래픽이 0**이다.

### 1.2 실측 근거 (Mixpanel, 2026년 6월 · 정상 운영 1개월)

| 지표 | 값 |
|---|---|
| D1 리텐션 | **13.9%** |
| D7 리텐션 | **2.0%** |
| 총 유입 75명 중 단일 방문 | **57명 (76%)** |
| 2회 이상 방문 | 12명 (16%) |
| 투표당 참여율 (6월 1주차) | 회원 19명 대비 평균 15명 = **79%** |
| 투표당 참여율 (6월 3주차) | 회원 30명 대비 평균 9.5명 = **32%** |

> 표본이 75명 규모라 소수의 이동으로 퍼센트가 크게 흔들린다. 위 값은 "이 정도는 돼야 개선됐다고 말할 수 있다"는 기준선이고, 통계적으로 유의미한 표본에서 검증된 값이 아니다.

리텐션 저하의 원인은 두 층으로 정리됐다 — **체감 가치 부족(메인)**, **콘텐츠 공급 부족(서브, 운영 문제 성격)**.

### 1.3 그래서 이번 작업이 잡은 문제

리텐션 자체는 제품 기능(승부예측·랭킹)의 몫이다. 이 문서가 다루는 건 **그 앞단의 두 병목**이다.

| # | 문제 | 실측 근거 |
|---|---|---|
| ① | **투표의 가치를 느끼기 전에 로딩에서 이탈한다.** 프로덕션 Lighthouse Performance 55 / LCP 14.2s (1차) → 리전 변경 후 73 / 14.4s (2차) | `20260819_lighthouse_분석.md`, `20260819_lighthouse_분석_리전변경후.md` |
| ② | **목표 규모에서 화면이 틀린 값을 보여준다.** 그런데 아무도 모른다 — 에러가 나지 않는다 | `20260825_백엔드_목표규모_트래픽생성_발표.md` §5 |

### 1.4 ②의 전제 — 잴 대상이 없었다

성능을 개선하려면 먼저 느려야 한다. 그런데 prod 실측 규모가 이렇다.

| 대상 | 실제 규모 |
|---|---|
| poll별 최대 표 수 | 1,000건 미만 |
| poll별 최대 평점 수 | **52건** |
| `rating_votes` 전체 | **52건** |

**52행짜리 테이블은 무엇을 어떻게 짜도 빠르다.** 인덱스를 붙여도, 집계를 DB로 내려도, 캐시를 붙여도 차이가 측정 한계 아래다. 그래서 부하 테스트의 질문을 바꿨다.

| | 흔한 질문 | 이 서비스에서 가능한 질문 |
|---|---|---|
| 묻는 것 | "지금 어디가 느린가" | **"목표 규모에서도 맞게 동작하는가"** |
| 종료 조건 | 병목 제거 | **목표 규모 시나리오 통과** |

> **작업 목적은 사후에 재정의됐다.** 8/19 원페이저의 목표는 "p95 개선"이었고, 8/21 1차 실측에서 개선할 성능이 없다는 것이 확인된 뒤 8/24에 "규모 가정 검증"으로 바뀌었다. 계획서·1차 결과·2차 설계가 모두 남아 있으므로 이 순서를 숨기지 않는다 — 사후 정립 자체는 흠이 아니지만 은폐는 흠이다. (`20260824_포트폴리오_서사_정립.md` §3, §9)

### 2.2 데이터 흐름 (① 이후 현재 구조)

```
사용자 요청
  └─▶ Next.js 서버 (Vercel)
        ├─ page.tsx (서버 컴포넌트)  ── Promise.all ─┬─ lib/queries/*  ──▶ Supabase PostgREST
        │                                            └─ unstable_cache(TTL)
        ├─ HTML / RSC 생성 (데이터가 이미 채워진 상태)
        └─▶ 브라우저 수신 → 표시 → *Client 컴포넌트 hydration

쓰기: 사용자 액션 ─▶ lib/actions/* (Server Action)
                      ├─ 서버 재검증 (마감·후보·배당)

```

- **조회와 쓰기가 디렉토리 단위로 분리**돼 있다 (`lib/queries/*` ↔ `lib/actions/*`).
- **"껍데기는 서버, 상태는 클라이언트"** 경계: 데이터 조회는 `page.tsx`, 상호작용은 `HomeClient` 등으로 내려 props로 받는다.
- Mock/실연동 모드는 `lib/config.ts`가 결정한다 — `NEXT_PUBLIC_SUPABASE_URL`이 없거나 `http`로 시작하지 않으면 `IS_MOCK = true`.

## 3. 설계 판단과 맞바꾼 것

각 판단은 **얻은 것 / 내준 것**을 같이 적는다. 내준 게 없는 판단은 판단이 아니라 그냥 작업이다.

### 3.1 조회를 브라우저 `useEffect` → 서버 컴포넌트로 옮겼다

**Before** — 데이터 요청 기준으로 직렬이다.
```
HTML 수신 → JS 번들 다운로드 → React 실행 → useEffect → 여기서야 Supabase 요청 → 데이터 도착 → 화면
```
이 구조에서는 **Supabase 쿼리를 아무리 빠르게 만들어도** 빈 화면 시간이 줄지 않는다. 병목이 쿼리가 아니라 **출발선**에 있다.

**After** — 서버가 HTML을 만들기 전에 조회하고, 의존 없는 조회는 `Promise.all`로 함께 발사한다(지연이 합이 아니라 최댓값이 된다).

```tsx
// frontend/src/app/page.tsx
export const revalidate = 30

export default async function HomePage() {
  const [sections, fixture] = await Promise.all([
    getPollHomeSections(),
    getHomeMatchdayFixture(),
  ])
  return <HomeClient sections={sections} fixture={fixture} />
}
```

| | |
|---|---|
| 얻은 것 | LCP 14.4s → 4.89s (①만의 몫) |
| **내준 것** | **옮겨온 조회 시간이 그대로 TTFB로 청구된다.** 그래서 3.2가 별개 작업이 아니라 짝이다 |
| 내준 것 | 상호작용 코드를 `*Client`로 분리해야 한다 — 껍데기/내용 경계를 매 화면마다 다시 그어야 했다 |

### 3.2 캐싱은 ①의 청구서를 막는 장치다 — TTL을 데이터 성격으로 나눴다

| 데이터 | TTL | 파일 | 근거 |
|---|---|---|---|
| 홈 투표 섹션 / 투표 목록 | 30초 | `lib/queries/polls.ts:263,340` | 참여 수가 계속 변함 — 최신성 우선 |
| 홈 경기 정보 | 30초 | `lib/queries/fixtures.ts:247` | 홈 라우트 `revalidate=30`과 정렬 |
| 예측 랭킹 | 60초 | `lib/queries/predictions.ts:151,192` | 집계값, 초 단위 최신성 불필요 |
| 경기 주차 / 평점 변동 | 300초 | `fixtures.ts:278`, `player-pick-one.ts:81` | 하루 단위로 바뀜 |
| 선수 후보 명단 | 3600초 | `lib/queries/squads.ts:92` | 사실상 시즌 단위 고정 |
| **내 예측 제출 내역** | **캐시 제외** | `predictions.ts:48` | 사용자별 데이터 — **캐시가 남의 예측을 보여주면 성능이 아니라 사고다** |

| | |
|---|---|
| 얻은 것 | 서버 응답 **21ms** — 조회를 서버로 옮겼는데도 TTFB가 낮다는 실측 증거 |
| **내준 것** | 홈 캐러셀의 집계 숫자는 최대 30초 지연된다. 투표 제출은 `/polls/{id}`만 무효화하고 **홈은 무효화 대상이 아니다 — 의도된 선택** |

### 3.3 라우트의 `revalidate`와 안쪽 `unstable_cache`를 같이 걸었다

라우트 쪽 선언이 없으면 **바깥 정적 라우트가 안쪽 `unstable_cache(30)`을 삼킨다.** 실제로 `/polls`와 `/`가 `○ (Static)`으로 굳어 참여자 수가 빌드 시점 값에서 영구히 멈춰 있었다.

- 조치: `app/polls/page.tsx:7`, `app/page.tsx:8`에 `export const revalidate = 30`
- 검증: `.next/prerender-manifest.json` → `/polls: 30`, `/: 30`
- 원 문서(`20260824_nextjs_렌더링_캐싱_점검.md` 1.3)는 `/polls`만 지목했으나 **홈도 같은 버그였다** — 같은 `unstable_cache(30)`을 쓰는 정적 라우트였다.

### 3.4 눈에 안 보이는 정책은 테스트로 고정했다

캐싱·프리페치 정책은 화면에 나타나지 않아 리팩터링에 조용히 지워진다.

- `lib/queries/cache-policy.test.mjs` — 공개 쿼리 모듈에 `unstable_cache`가 살아 있는지 검사
- `components/prefetch-policy.test.mjs` — 하단 네비·투표 카드의 `prefetch={false}` 고정 (카드 20개면 프리페치도 20번 나간다)

| | |
|---|---|
| 얻은 것 | 정책이 조용히 빠지는 걸 막는다 |
| **내준 것** | **이 테스트들은 소스 문자열을 정규식으로 검사한다 — 렌더링 테스트가 아니다.** 화면 구조를 옮기면 로직이 옳아도 깨진다. 실제로 2026-08-24에 화면 구조가 바뀐 뒤 4건이 깨진 채 방치됐다 |

### 3.5 인덱스 9개를 **지금 붙이지 않기로** 판정했다

목표 규모 부하 실측에서 현실 피크 p95가 전부 200ms 미만이었고 여유가 약 77배였다. **근거 있는 미실행이 근거 없는 실행보다 낫다.**

| | |
|---|---|
| 얻은 것 | 불필요한 인덱스 유지비·쓰기 비용을 안 낸다 |
| **내준 것** | DAU 7,700을 넘기면 다시 재야 한다. 이 판단은 **DAU 100 목표 기준에서만** 유효하다 |

### 3.6 1,000행 캡을 RPC가 아니라 **뷰**로 풀었다

`.rpc()`는 리포 내 사용처가 0건이지만, **뷰는 이미 있는 개념이다** — `week_leaderboard`·`season_leaderboard`·`prediction_results`가 있고 `types/database.ts`에 `Views` 슬롯도 열려 있다. 새 개념을 들이지 않았다.

- `supabase/migrations/20260825120000_rating_poll_participants.sql` — `count(distinct user_id)` 집계 뷰, `security_invoker = true`로 기존 `rating_votes: public read` 정책을 그대로 탄다
- `lib/queries/polls.ts:96` — 전량 select + JS `Set` → 뷰 조회 1회. **응답 행 수가 poll 수와 같아 캡에 닿지 않는다**
- 검증: service_role뿐 아니라 **앱의 실제 경로인 anon 키로 다시 확인**(200) — service_role만으로 확인하면 RLS/권한 누락을 놓친다

### 3.7 `getRatingResults`(A-2)는 **보류**했다

멈춘 이유는 측정 데이터 부재가 아니라 **대상이 움직이기 때문**이다. 평점 결과 화면의 기획이 변경 예정이고, 필요한 쿼리 형태가 화면에 직접 매여 있다(선수별 상위 3개 / "전체보기" 전량 펼침 / 좋아요순 정렬). 화면 확정 전에 뷰를 짜면 그 뷰를 다시 짜게 된다.

- 발현 임계는 **한 투표의 참여자 71명**(1,000 ÷ 14선수)이고 prod 현재 참여자 2명이라 여유가 있다.
- 화면이 어떻게 바뀌어도 유지될 방향은 정해뒀다 — **점수(집계)와 코멘트(목록)를 분리**한다. 저장 성질이 다르다(점수는 전원 필수 14행, 코멘트는 선택·대부분 `null`).
- 「근거 미확인」: 코멘트 상한을 어떻게 잡을지는 **코멘트가 달린 행의 비율**에 달렸는데, staging 시드에 코멘트가 없고 prod는 참여자 2명이라 **실측할 데이터가 아직 어디에도 없다.**

### 3.8 정산은 테이블을 만들지 않고 뷰 + 조건절로 끝냈다

점수는 배당 스냅샷(`predictions.*_multiplier`) + 평점(`fixture_player_ratings`)으로 **완전히 파생**된다. 필요한 건 저장이 아니라 **노출 시점 통제 하나**였다.

| | |
|---|---|
| 얻은 것 | 산식을 고치면 과거 경기 점수까지 같이 따라온다 |
| **내준 것** | 랭킹 조회가 무거워지면 matview로 승격해야 한다 — 지금은 미룬 결정이다 |

또한 **정산 시점을 크론 스케줄로 잡지 않았다.** 취소·연기 경기(FotMob이 `cancelled`를 내려주고 킥오프가 다음 주로 밀리는 경우)에서 바로 어긋나기 때문이다. **데이터 상태로 판정하면 그게 알아서 맞는다.**

### 3.9 마감은 세 겹으로 막았다

`submitWeekPrediction`(`lib/actions/predictions.ts`)의 방어:

1. **서버 재검증** — 마감·후보·배당을 서버가 다시 계산한다. 클라이언트에서 받는 값은 스코어와 선수 id뿐이다.
2. **RLS 정책** — `predictions: insert own while week open`이 `f.started = false and f.kickoff_at > now()`를 `with check`로 강제한다. 위반은 `42501` → `'closed'`.
3. **UNIQUE 제약** — `23505` → `'already_submitted'` (제출 후 수정 불가).

주 단위 제출은 **다중 행 insert 한 statement**로 넣는다 — 부분 제출(픽이 한쪽 경기에만 붙는 상태)이 생기지 않는다. 별도 테이블·트랜잭션 없이 해결된다.

> 「기록된 한계」: "같은 주의 행들은 픽이 같다"는 **DB 제약이 아니라 서버 액션의 불변식**이다. `predictions`에 쓰는 경로가 그 액션뿐이라 지금은 충분하지만, 관리자 직접 입력 같은 다른 쓰기 경로가 생기면 `(user_id, week_start)` 부모 테이블로 승격해야 한다. (마이그레이션 주석에 명시)

### 3.10 부하 규모를 **임의의 큰 숫자 대신 서비스 목표에서 유도**했다

```
목표: 서비스 사용자 100명 (DAU) × 운영 중인 투표 10개 × 1인 1투표(UNIQUE 강제) = 1,000표
```

1차(8/21)는 유저 10만 명 / 표 10만 개로 시드했다. 결함은 나왔지만 **prod의 약 2,000배**였다.

| | 10만 표 | 1,000표 (목표 규모) |
|---|---|---|
| 말할 수 있는 것 | "언젠가 이런 일이 생길 수도 있다" | **"지금 이걸 고쳐야 한다"** |
| 규모의 근거 | 없음 (지어낸 수) | 사업 목표 — **틀렸다면 사업 목표가 틀린 것이지 측정이 틀린 것이 아니다** |

여기서 **첫 발견**이 나왔다. 같은 "1인 1표"인데 저장되는 행 수가 유형별로 다르다.

| 유형 | 제출 1회당 행 수 | 100명 × 5개 |
|---|---|---|
| 선택형 (`selection`) | `votes` **1행** | 500행 (poll당 100행) |
| 평점형 (`overall_rating`) | `rating_votes` **선수 수만큼(14)** | **7,000행** (poll당 1,400행) |

> 같은 "사용자 100명"인데 한쪽은 100행, 다른 쪽은 1,400행이다. **사용자 수만 보고 규모를 가늠하면 14배를 놓친다.**

### 3.11 시드에서 `random()`을 금지했다

1차 시드는 `ORDER BY random() LIMIT 1` 상관 서브쿼리가 한 번만 평가돼 **10만 표가 전부 한 선택지에 몰렸다.** 그래서 결정적 배정으로 바꿨다 — 선택지는 `ui % 선택지수`, 점수는 `(선수순번 + 사용자순번) % 6`.

또한 스크립트 상단에 **staging 가드**를 넣었다. `SUPA_URL`에 staging ref가 없으면 즉시 중단한다 — prod에 실행되면 기존 데이터를 지운다.

### 3.12 엔드포인트를 태그로 나눠 측정했다

1차의 교훈이다. 캐시된 목록(3.62ms)과 비캐시 상세(290ms)를 합치면 **80배 차이가 사라진다.** 선택형과 평점형은 행 증가율이 14배 다르므로 `detail-rating` 태그로 분리했다.

### 5.4 ② 정확성 — 개선 전후

목표 규모를 시드한 뒤 `/polls` 목록을 **실제로 렌더**한 결과:

| 투표 | 개선 전 화면 표시 | 정답 |
|---|---|---|
| 이주의 선수 1~5R (선택형) | 100 / 100 / 100 / 100 / 100 | 100 |
| **경기 평점 1~5R (평점형)** | **0 / 0 / 0 / 0 / 72** | **각 100** |

**평점 투표 참여 500건이 화면에는 72건으로 나왔다. 5개 중 4개는 "아무도 참여하지 않음"이었다.**

뷰 전환(3.6) 후 같은 시드로 재조회:

| | HTTP | 응답 | 결과 |
|---|---|---|---|
| **개선 전** (전량 select + JS `Set`) | 206 ※ | `Content-Range: 0-999/7000` | 5개 중 1개만 인식(72) + **4개 응답에 아예 없음** |
| **개선 후** (`rating_poll_participants` 뷰) | 200 | `Content-Range: 0-4/5` | **평점 poll 5개 전부 100** |

| 항목 | 개선 전 | 개선 후 |
|---|---|---|
| 참여자 500명 표시 | **72명 (4개는 0명)** | **500명 (각 100)** |
| 앱→DB 전송량 | 103 KB (캡된 1,000행) | poll당 1행 (5행) |
| 캡 도달 여부 | 도달 — 7,000행 중 1,000행 | **응답 행 수 = poll 수라 구조적으로 도달 불가** |

> ※ **HTTP 상태 기록이 두 문서에서 엇갈린다.** `20260825_백엔드_목표규모_트래픽생성_발표.md` §5.2는 `200`, `20260825_백엔드_코드수정_리스트업.md` A-1·A-2 재실측은 `206 Partial Content`로 적었다. 어느 쪽이든 **Supabase 클라이언트가 던지지 않는 성공 계열 응답이고 `error` 필드가 비어 있어 코드에서 잡히지 않는다** — 결함의 성질은 같다. 정확한 상태 코드는 재확인 대상으로 남긴다.

세 경로의 판정 (개선 전 기준):

| 경로 | 함수 | 실제 행 | 수신 행 | 판정 |
|---|---|---|---|---|
| 목록 참여자 수 | `getRatingParticipantCounts` (`polls.ts:87`) | 7,000 | 1,000 | **깨짐** → ✅ 수정 완료 |

## 6. 평가 리포트 — 실패 원인 분석

찾은 결함은 **전부 에러를 내지 않는다.** 그래서 지금까지 아무도 몰랐다.

| 겉보기 | 실제 |
|---|---|
| HTTP 200, 정상 배열 | 집계가 틀림 |
| 화면에 "0명" | 100명이 참여했음 |
| 에러율 0% | 사용자는 5.58초 대기 |
| 정상 숫자 | 빌드 시점에 정지 |

### ① 1,000행 캡 — 성공 코드를 반환하는 절단

```
GET /rest/v1/rating_votes?select=poll_id,user_id&poll_id=in.(평점 poll 5개)
→ HTTP 200 / 206              ← 문서 간 기록 불일치 (5.4의 ※ 참고). 어느 쪽이든 성공 계열
   Content-Range: 0-999/7000  ← 7,000행 중 1,000행만
   103 KB
```

- **원인**: Supabase 호스팅이 넣는 PostgREST `db-max-rows = 1,000`. **PostgREST 자체 기본값은 무제한이다** — 즉 문서를 읽어도 안 나오고, 호스팅 설정을 봐야 나온다.
- **왜 안 걸렸나**: (a) 에러가 아니다 — 성공 계열 응답에 `error` 필드 없음, 예외도 로그도 없다 (b) 작은 데이터에서는 맞는다 — prod 현재 52건에서는 정확하다 (c) **정적 페이지에 굳는다** — `/polls`가 `○ (Static)`이라 잘린 집계가 빌드 시점에 고정돼 그대로 서빙된다
- **임계값 — 먼 얘기가 아니다**:

| 선수 수 | 목록에 평점 투표 1개 | 5개 |
|---|---|---|
| 11명 | 90명에서 깨짐 | **18명** |
| **14명** | 71명 | **14명** |
| 25명 | 40명 | **8명** |

> 선수 14명 기준, 목록에 평점 투표 5개면 **참여자 14명에서 이미 틀린다. "사용자 100명"은커녕 지인 테스트 규모에서 넘는다.** prod가 아직 안 걸린 건 평점 투표 자체가 적어서다.

- **왜 임베디드 집계로 안 됐나**: 필요한 건 `COUNT(DISTINCT user_id)`인데 `count()`는 행 수라 **선수 수만큼 과다 집계**된다. 그래서 뷰가 필요했다.

### ② hydration mismatch — 서버 렌더링의 이점을 반납하고 있었다

3·4차에서 React `#418`/`#423`/`#425` 콘솔 에러 **6건**이 청크 해시까지 동일하게 남아 있었다. `#423`은 **SSR HTML을 버리고 root 전체를 클라이언트에서 다시 그리는 상태**다.

- **원인**: 날짜/시각 포맷터 6곳에 `timeZone`이 없어 서버(UTC)와 브라우저(KST)의 출력이 달랐다. 사실상 `formatKickoff` 한 곳.
- **조치**: `timeZone: 'Asia/Seoul'` 고정 (커밋 `f4f2443`)

| | 4차 (재렌더 있음) | 5차 (재렌더 없음) |
|---|---|---|
| `errors-in-console` | score 0 / 에러 6건 | **score 1 / 0건** |
| FCP | 2,415 ms | **1,161 ms** |
| LCP `elementRenderDelay` | 291 ms | **45 ms** |

**`timeZone` 고정만으로 6건 전부 사라졌다.** 3차에서 "#425는 사실상 `formatKickoff` 한 곳"이라고 지목한 진단이 맞았고, "재렌더가 개선 효과를 먹고 있다"는 추정이 **실측으로 확인된 인과**가 됐다.

> 남은 것: `Date.now()` 계열은 이번 측정에서 mismatch를 만들지 않았지만, **날짜 경계를 넘는 순간에만 재현되는 종류**다. 안 잡힌 것이 해결됐다는 뜻이 아니다.

### ③ 4차에서 Performance 80 → 77로 내려갔다 — 원인 귀속이 아직 하나로 모이지 않았다

숨기지 않고 4차 리포트에 그대로 적었다. 측정 조건은 동일했다. 다만 **원인 설명이 문서마다 다르다.**

| 문서 | 지목한 원인 |
|---|---|
| `20260826_lighthouse_분석_4차.md` | **홈 히어로 콘텐츠가 매일 바뀌는 것** + 폰트 |
| `20260826_통합발표_구성안_5차반영.md` 부록 A | ②와 같은 **hydration 재렌더 구간** |
| `20260826_lighthouse_분석_5차.md` | 4차 하락의 원인을 단정한 문장 **없음** |

> **「근거 미확인」.** hydration 수정이 5차에서 큰 개선을 만든 것은 실측이지만(②), 그것이 **4차 하락의 원인이었다는 인과는 어느 리포트도 실측으로 확정하지 않았다.** 발표에서 이 질문을 받으면 두 귀속이 병존한다고 답하는 편이 안전하다.

### ④ Cache-Control 회귀 — 개선 작업이 만든 회귀

외부(fotmob) 이미지를 Supabase Storage로 이전하면서 **팀 로고의 캐시 수명이 7일 → 0**이 됐다. 재방문마다 히어로 상단 30KB를 다시 받았다.

- 조치: Storage 32개 파일 메타데이터 일괄 갱신 + 업로드에 `cacheControl: '31536000'` 추가
- 결과: `cache-insight` 절감 여지 **86KB → 2KB**. 남은 1건은 구글 프로필 이미지라 헤더를 건드릴 수 없다 — 사실상 종료.

### ⑤ 정적 페이지 고착 — 시간 가정이 깨진 사례

투표 제출(`submitVote`/`submitRatingVotes`)은 `/polls/{id}`만 무효화한다. `/polls`·`/`는 `revalidatePath` 대상이 아니었고 `revalidate` 선언도 없어 **정적 산출물에 굳어 있었다.** 참여자 수가 빌드 시점 값에서 영구히 안 움직였다. (조치: 3.3)

### ⑥ 에러율 0%인데 p95 5.58초 — 알람 사각지대

조건 C에서 평점형 상세가 p95 5.58초인데 에러율은 0.00%다. 서버가 요청을 거절하지 않고 **전부 받아 줄을 세운다.**

> **5xx만 모니터링하면 이 상태를 탐지할 수 없다. 사용자는 5초를 기다리는데 알람은 울리지 않는다.**

1차(10만 표 규모)에서 관찰한 특성이 목표 규모에서도 동일하게 나타났다 — **규모와 무관한 구조적 성질**이다. 그리고 이것이 지금 **관측성이 다음 최우선 과제인 이유**다(8절).

### ⑦ TBT 3ms → 265ms는 우리 코드가 아니다 — 측정 함정

| 지표 | 4차 | 5차 | 해석 |
|---|---|---|---|
| 메인스레드 총 작업 | 1.7 s | 1.7 s | 동일 |
| JS 실행(bootup) | 0.5 s | 0.5 s | 동일 |
| 최장 long task | 232 ms — `chrome-extension://…` | **232 ms — 같은 확장 프로그램** | 동일 |
| FCP | 2,415 ms | 1,161 ms | — |

**TBT는 FCP 이후의 블로킹만 센다.** 4차에서는 확장 프로그램의 232ms 태스크가 FCP보다 먼저 끝나 계산에서 빠졌다. 5차에서는 FCP가 1.25초 앞당겨지면서 그 태스크가 **측정 창 안으로 들어왔다.**

> **사이트를 빠르게 만든 결과로 점수가 나빠졌다.** TBT 가중치는 30점으로 단일 최대인데, **지금은 우리 코드의 실제 TBT를 알 수 없다.** 3·4차에서 "다음엔 시크릿 창으로"라고 두 번 적고 두 번 넘어간 것의 청구서다.

### ⑧ CLS 0.052 — 고쳐서 드러난 문제

`useCountdown`은 hydration mismatch를 막으려고 마운트 전 `null`을 돌려준다(3차 리포트가 "올바르게 막고 있다"고 본 가드다). 그래서 **서버 HTML에는 카운트다운 4칸이 없고**, 마운트 후 약 70px가 갑자기 생기며 투표 목록을 밀어낸다.

4차까지 CLS가 0.0002였던 건 **root 전체가 CSR로 다시 그려져 첫 페인트 자체가 마운트 이후였기 때문**이다. hydration을 고쳐 SSR HTML이 살아남자 원래 있던 문제가 드러났다.

> 즉 그 가드는 **mismatch 관점에서는 맞지만 CLS 관점에서는 대가가 있었다.** 기준 이내(0.1)라 감점은 1점이지만 첫 화면에서 목록이 툭 내려가는 게 눈에 보인다. 고치는 방향은 두 안(자리 미리 확보 / 서버에서 초기값 계산)으로 갈리며 **아직 결정하지 않았다.**

### ⑨ 1차 시드 실패 — `ORDER BY random()` 상관 서브쿼리

10만 표를 시드했는데 `ORDER BY random() LIMIT 1`이 한 번만 평가돼 **전부 한 선택지에 몰렸다.** 분포가 없는 데이터로는 집계를 검증할 수 없다. (조치: 3.11)

### ⑩ 부하 테스트는 이 결함들을 찾는 **효율적인 도구가 아니었다**

정직하게 적는다. 1,000행 캡은 `select()` 전수 grep으로 30분이면 나왔다. 발견 메커니즘별로 도구가 다르다.

| 메커니즘 | 적합한 도구 | 리포 실측 |
|---|---|---|
| 성공 코드를 반환하는 절단 | grep + 판정 | `select()` **28곳 중 `limit`/`range`가 5곳뿐** → 23곳 미확인 |
| 에러를 삼키고 기본값 반환 | 코드 리뷰 | `if (error` 38곳, 빈 기본값 반환 23곳 |
| 무효화 누락 | 액션 × 캐시 매트릭스 | 액션 12파일 전수 대조 미실시 |
| 환경 간 차이 | `pg_policies` 항목 단위 대조 | 방법만 확정 |
| **자원 고갈이 지연으로만 발현** | **k6** | **⑥에서 확인 완료** |

**k6가 실제로 필요한 건 마지막 하나뿐이었고, 그건 이미 했다.** 부하 테스트가 헛수고였다는 뜻은 아니다 — 캡을 발견하게 만든 계기가 대규모 시드였다. 다만 **발견 이후에는 도구를 바꾸는 것이 맞다.**

### 7.3 판단 자체의 한계

- **테스트가 소스 문자열 검사다.** 정책 회귀는 잡지만 렌더링 결과는 검증하지 않는다. 화면 구조를 옮기면 로직이 옳아도 깨진다(3.4).
- **`types/database.ts`가 수동 관리다.** `types:supabase`로 생성한 파일과 별도라 drift 위험이 상시 존재한다.
- **"같은 주의 픽은 같다"가 DB 제약이 아니다.** 서버 액션의 불변식이라 다른 쓰기 경로가 생기면 깨진다(3.9).
- **마이그레이션 두 개가 서로 반대를 말한다.** 인덱스 9개를 만드는 마이그레이션과 drop하는 `remote_schema.sql`이 함께 있고, 이 상태가 원격에도 반영돼 있다.
- **77배는 DAU 100 목표 기준이다.** 목표가 바뀌면 이 판단(3.5)도 같이 무효가 된다.

### C-2 상세 — A-1이 prod에 살아 있다는 근거

A-1 수정은 **두 개의 배포 경로**를 가진다. 하나만 확인하면 반쪽이다.

| 경로 | 무엇이 나가는가 | 확인 방법 | 결과 |
|---|---|---|---|
| **코드** — `polls.ts:96`이 뷰를 조회 | Vercel(main 브랜치) | 아래 ①② | **반영됨** |
| **DB** — `rating_poll_participants` 뷰 | `supabase db push` (Vercel과 무관) | 아래 ③ | **반영됨** |

**① 커밋 조상 관계** — A-1 커밋 `6e54df9`(8/25 15:10)는 `acd2273`(8/25 17:24)로 main에 병합됐고, main 헤드 `ffcc3f7`(8/26 10:45)의 **조상**이다. 즉 `ffcc3f7`을 배포한 빌드는 `6e54df9`를 **반드시 포함한다.**

**② 5차 측정이 그 배포를 증명한다** — 5차(8/26 10:48)는 prod URL 실측이고, `errors-in-console`이 **0건**이다. hydration 에러를 없앤 `timeZone` 고정은 `f4f2443`(10:33 커밋 → 10:45 병합)의 코드 변경이므로, **10:48 시점의 prod가 이미 새 빌드를 서빙하고 있었다는 뜻이다.** ①과 합치면 A-1 코드도 함께 나가 있다.

> 이 논증의 방향에 주의: "hydration이 고쳐졌다"가 "A-1도 배포됐다"를 함의하는 이유는 **둘이 같은 배포에 실려 있어서**다(조상 관계). 별개 근거를 두 개 모은 게 아니라 하나의 배포 사실을 확인한 것이다.

**③ 뷰는 별도로 확인됐다** — Vercel 배포는 마이그레이션을 밀지 않으므로 코드만 나가고 뷰가 없으면 조회가 깨진다. 이건 8/25에 따로 확인했다: `supabase migration list`에서 `20260825120000`이 **local = remote**, 그리고 **prod ref(`xrvz…`)에서 anon 키로 뷰 조회 200**(`participant_count: 2` — prod 현재 참여자 수와 일치). service_role만으로 확인하면 RLS/권한 누락을 놓치므로 앱의 실제 경로인 anon으로 확인했다.

**남는 한계** — Vercel 배포 이력 자체는 직접 열어보지 않았다. 위 논증은 **prod 실측 결과(5차 리포트)에서 배포 사실을 역추론**한 것이다. 결론은 같지만 근거의 종류는 다르다.

> 다만 이 논증이 보증하는 것은 **A-1이 prod에 살아 있다**는 것뿐이다. 발표에서 인용하는 재실측 수치(**평점 poll 5개 전부 100**)는 여전히 **staging에서 목표 규모를 시드해 얻은 값**이다 — prod에는 참여자가 2명뿐이라 그 규모를 prod에서 재현할 수 없다. 이 구분은 유지한다.
