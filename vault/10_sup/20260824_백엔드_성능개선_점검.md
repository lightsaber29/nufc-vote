## 0. 전제 — 인프라 구조상 병목이 생기는 자리

Vercel 서버리스 → Supabase **PostgREST(REST)** 구조다. 앱이 Postgres에 직접 커넥션을 열지 않으므로 커넥션 풀 고갈 문제는 없고, 병목은 세 가지로만 나타난다.

1. **요청당 왕복 횟수** — 왕복 1회당 약 28ms (분석 문서 6.2 실측)
2. **앱으로 끌어오는 행 수** — 전송량 + JS 집계 비용, 그리고 1,000행 캡(정확성 버그)
3. **매 요청 재계산되는 view** — 캐시 없는 집계 view

아래 항목은 전부 이 셋 중 하나에 속한다.

## P0-2. 랭킹 view가 매 요청 전체 재계산된다

`queries/predictions.ts:139` `getWeekRanking()`:

```ts
supabase.from('week_leaderboard')
  .select(...)
  .eq('week_key', weekKey)   // ← group by 뒤에 걸리는 필터
  .order('rank')
```

`week_leaderboard`(`20260823140000_week_leaderboard.sql`)는 내부에서 `prediction_results`를 주차별로 `group by`한다. `week_key`는 `to_char(date_trunc(...))` 집계 그룹 키이므로 필터가 **집계 아래로 내려가지 않는다.** 즉 한 주차만 보는 요청이 매번 아래를 전부 계산한다.

```
predictions
  ⋈ fixtures
  ⟕ fixture_player_ratings (DEF)
  ⟕ fixture_player_ratings (MID)
  ⟕ fixture_player_ratings (FWD)
  → 종료 경기 전량에 대해 점수 함수 평가 → 주차 group by → rank() window
```

`season_leaderboard`도 같은 구조로 종료된 전 경기를 누적한다. 게다가 **`getWeekRanking`/`getSeasonRanking` 둘 다 `unstable_cache`가 없어 요청마다 실행된다** — 같은 파일의 `getMyPredictions`/`getMyResults`는 사용자별 데이터라 캐시하지 않는 게 맞지만, 랭킹은 전원 공용 데이터라 캐시하지 않을 이유가 없다.

호출 지점: `/predictions`(시즌 랭킹, 목록 진입마다), `/predictions/[weekKey]` 종료 주차(주차 랭킹).

### 개선 (라지 순)

1. **두 함수를 `unstable_cache(revalidate: 60)` + 태그로 감싼다.** 랭킹은 평점 입력 시에만 바뀌므로, `actions/fixture-ratings.ts`의 `saveFixtureRatings`에서 `revalidateTag`를 호출하면 신선도도 유지된다. 진짜 변경은 몇 줄이다.
2. 규모가 커지면: `predictions`에 주차 키를 generated column으로 올리고 인덱스를 걸어 필터가 집계 아래로 내려가게 하거나, materialized view + 평점 저장 시 refresh.

주의: `week_key` 문자열 기준은 `lib/predictions/week.ts`의 `weekKey()`와 view의 `IYYY-IW`가 **같은 값이어야 한다.** generated column을 도입하면 기준이 세 곳으로 늘어난다 — 1번(캐시)이 이 위험을 만들지 않는 이유이기도 하다.

## P0-3 / P1-4 / P1-5. 행 전량 조회 3건 — 기존 계획 미착수

`20260821_백엔드_성능개선_수정계획.md`가 이미 다룬 3건이며, **코드는 아직 수정 전이다.** 계획서의 채택안(임베디드 집계 `votes(count)`)이 여전히 유효하다.

| 위치 | 함수 | 현재 동작 |
|---|---|---|
| `queries/polls.ts:335` | `getVoteCounts` | `option_id` 행 전량 → JS `reduce` |
| `queries/polls.ts:88` | `getRatingParticipantCounts` | `(poll_id, user_id)` 전 행 → JS `Set`으로 distinct |
| `queries/polls.ts:381` | `getRatingResults` | 한 표의 평점 행 **무제한** 조회 → 선수별 `filter` (O(선수수 × 투표수)) |

정확성(1,000행 캡)과 성능이 같은 방향으로 풀리는 건이므로 계획서 그대로 진행한다. 코드 정적 점검에서 추가로 보이는 점만 덧붙인다.

- `getRatingParticipantCounts`의 행 수는 **표 수 × 선수 25명 × 참여자 수**로 곱셈으로 늘어난다. 목록 페이지 30초 캐시가 현재 이걸 가리고 있다.
- `getRatingResults`는 같은 파일의 `getComments`가 `limit(50)`을 두는 것과 달리 **상한이 전혀 없다.** 임베디드 집계로 못 줄이는 코멘트 본문까지 전량 받으므로, 선수별 상위 N개만 가져오는 형태가 필요하다.

## P1-6. `getCreatorNamesById` — 요청마다 service-role 클라이언트 생성

`queries/polls.ts:130`:

```ts
const { createClient: createServiceClient } = await import('@supabase/supabase-js')
const supabase = createServiceClient(url, SERVICE_ROLE_KEY)   // 호출마다 새로 생성
await supabase.from('users').select('id, display_name').in('id', uniqueIds)
```

목록(`getPollList`)과 상세(`getPollById`) 양쪽에서 호출된다. 문제 세 가지가 겹쳐 있다.

1. 동적 import + 클라이언트 인스턴스 생성이 매 호출 반복된다.
2. 작성자 이름 하나 때문에 **왕복 1회(≈28ms)**가 추가된다.
3. 공개 목록 조회 경로에서 **service-role 키를 쓴다** — RLS를 통째로 우회하므로 성능과 별개로 줄여야 할 표면이다.

→ 댓글 쿼리(`queries/comments.ts`)가 이미 쓰는 `public_profiles` FK 조인 패턴으로 본 쿼리에 합치면 세 문제가 같이 사라진다. `AGENT_MAINTENANCE_GUIDE.md`의 "댓글 작성자 표시는 `public_profiles`를 사용" 원칙과도 같은 방향이다.

## P1-7. `auth.getUser()` 중복 왕복

`getUser()`는 Supabase Auth 서버로 나가는 **네트워크 왕복**이다. 요청 하나에서 여러 번 호출된다.

`/predictions` 진입 시:

| 호출부 | 위치 |
|---|---|
| middleware | `middleware.ts:49` (보호 경로만 — `/predictions`는 해당 없음) |
| `getMyPredictions` | `queries/predictions.ts` |
| `getSeasonRanking` | `queries/predictions.ts` (top/mine 조회 전에 1회) |

`/predictions/[weekKey]` 종료 주차는 `getMyPredictions` + `getMyResults` + `getWeekRanking` = **3회**, `/my`·`/admin` 계열은 middleware까지 더해진다. `Promise.all`로 병렬화돼 있어 지연이 합산되지는 않지만, 왕복 자체와 Auth 서버 부하는 그대로 쌓인다.

→ `React.cache()`로 감싼 `getUser` 헬퍼 하나를 만들어 query들이 그걸 쓰게 한다. 요청 스코프 내 1회로 줄고, 디프는 매우 짧다.

## P1-8. `getComments` 순차 왕복 4회

`queries/comments.ts`의 흐름:

```
comments (본 쿼리)
  → votes      (댓글 작성자들의 투표 항목)      ← comments 결과 의존
  → poll_options (항목 라벨)                    ← votes 결과 의존
  → comment_likes (내가 좋아요한 댓글)          ← comments 결과에만 의존
```

앞 세 개는 진짜 의존 체인이지만, **`comment_likes` 조회는 votes 체인과 독립적**이라 지금 순차로 기다릴 이유가 없다. votes 체인과 `Promise.all`로 묶으면 왕복 4 → 3(체인 길이 기준)으로 줄어든다. 약 28ms 절감.

현재 규모에서 이 경로의 비용은 **DB 실행시간이 아니라 왕복 수**다. 같은 경로의 인덱스를 되살리는 건 도움이 되지 않는다(P2-1).

`queries/fixtures.ts`는 필터 없이 `fixtures` 전 행을 12개 컬럼으로 읽어 `kickoff_at` 정렬한다. 현재는 300초 캐시가 가리고 있으나 시즌이 쌓이면 선형으로 증가한다.

## P2-10. `submitVote` 왕복 4회

`actions/vote.ts`: poll 조회 → poll_option 조회 → insert → (첫 투표 판정용) count.

## P2-1. 핫 쿼리 인덱스 9개 — 지금은 붙이지 않는다

`20260624130000_add_hot_query_indexes.sql`이 만든 인덱스 9개를 `20260821092457_remote_schema.sql:11-27`이 `drop index if exists`로 전부 지우고, 이후 재생성하는 마이그레이션이 없다.

```
votes_poll_id_idx                            comment_likes_user_comment_idx
votes_poll_id_user_id_idx                    rating_vote_likes_user_vote_idx
comments_visible_poll_created_at_idx         rating_votes_poll_id_idx
player_pick_one_weekly_runs_applied_week_end_idx    rating_votes_poll_user_idx
player_pick_one_rating_changes_run_delta_idx
```

이 문서 초안은 이걸 P0로 올렸다. **틀렸다. 현재 규모에서 인덱스는 이득이 없고, 오히려 약간 손해다.**

### 왜 이득이 없나 — 실측 규모

`20260821_백엔드_성능테스트_결과_분석.md` 4.5의 prod 실측: `rating_votes` **전체 52건**. `votes`·`comments`도 같은 자릿수다.

52행 테이블에서 seq scan은 힙 페이지 1개를 읽고 끝난다. 인덱스 스캔은 인덱스 페이지 + 힙 페이지를 읽으므로 I/O가 오히려 늘고, 플래너도 그걸 알기 때문에 **인덱스를 만들어도 선택하지 않는다.**

같은 문서가 이미 인덱스 두 건을 실효 없음으로 판정했다 — 6.3(`polls` 정렬, 절감 약 1.9ms), 6.4(`votes` 전량 집계는 Seq Scan이 옳음). 나머지 인덱스도 같은 논리가 적용된다.

### 오히려 손해인 쪽

`votes` insert는 사용자 투표라는 핫패스다. `votes_poll_id_idx` + `votes_poll_id_user_id_idx`가 있으면 insert마다 인덱스 2개를 갱신한다. 50행 규모에서 읽기 이득 없이 쓰기 비용만 붙는다.

### 그래도 남는 것 — 성능이 아니라 drift

실제 문제는 인덱스의 부재가 아니라 **마이그레이션 두 개가 서로 반대를 말하고 있다**는 것이다. `20260624130000`은 만들고 `20260821092457`은 지운다. 8/21 pull 사고(분석 문서 5장)와 같은 종류의 혼란이 다음 사람에게 반복된다 — 이 문서 초안 자체가 그 파일 두 개만 보고 "prod에 인덱스가 없다"고 잘못 단정한 사례다.

인덱스 9개를 되살려 풀 문제가 아니다. **어느 쪽으로 정했는지 기록만 하면 끝난다** — 문서 한 줄이 마이그레이션 9줄보다 싸다. (참고: 분석 문서 6.4는 8/21 시점 staging에 `votes(poll_id)`가 존재했다고 관찰했다. pull 산출물과 어긋나지만, 어느 쪽이든 붙이지 않기로 정했으므로 규명할 필요가 없어졌다.)

### 언제 붙이나 — 임계값 하나

**poll당 행이 1,000을 넘어갈 때.**

이 숫자는 우연이 아니다. PostgREST `db-max-rows` 캡이 터지는 지점과 같으므로, **P0-3/P1-4/P1-5(집계를 서버로 옮기는 작업)를 착수해야 하는 시점 = 인덱스가 의미를 갖기 시작하는 시점**이다. 그때 같이 붙인다. 지금은 아니다.

붙일 때 실효가 있는 것은 선택도가 높은 경로에 한한다(전량 집계 경로는 그때도 Seq Scan이 옳다):

| 인덱스 | 실효 경로 |
|---|---|
| `votes_poll_id_user_id_idx` | `getMyVote` — `.eq(poll_id).eq(user_id)` |
| `comments_visible_poll_created_at_idx` | `getComments` 본 쿼리 — `poll_id + is_hidden + created_at desc` |
| `comment_likes_user_comment_idx` | `getComments` 좋아요 — `.eq(user_id).in(comment_id)` |
| `rating_votes_poll_user_idx` | `getMyRatingVoteCount` — `.eq(poll_id).eq(user_id)` |
