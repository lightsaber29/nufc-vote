## 1. 라우트 분류 실측 — `/polls`는 캐시가 아니라 정적이다

### 1.1 빌드 출력

```
┌ ○ /                        Static
├ ○ /polls                   Static
├ ○ /players                 Static (revalidate 60)
├ ○ /players/changes         Static (revalidate 3600)
├ ƒ /polls/[id]              Dynamic
├ ƒ /predictions             Dynamic
├ ƒ /predictions/[weekKey]   Dynamic
├ ƒ /my, /menu, /admin ...   Dynamic
```

`app/polls/page.tsx`는 `cookies()`·`headers()`를 쓰지 않는다. Next.js App Router는 이 경우 **빌드 시점에 HTML을 프리렌더**한다.

### 1.2 1차 문서 2.1의 해석 정정

1차 결과 분석 2.1은 이렇게 적었다:

> `/polls`는 `getPollList`가 `unstable_cache(revalidate:30)`로 감싸져 있어 3분간 DB를 치는 건 약 6회뿐이다. 1.65ms는 캐시 히트 비용이다.

**틀렸다.** `/polls`가 정적 라우트이므로 측정 구간 동안 **DB 접근은 0회**이고, 1.65ms는 프리렌더된 HTML을 내보내는 비용이다. `unstable_cache(revalidate: 30)`는 바깥 정적 라우트에 갇혀 **아예 실행되지 않는다.**

결론(= 목록은 최적화 대상이 아니다)은 그대로 유효하다. 이유가 "캐시가 잘 듣는다"에서 "애초에 DB를 안 친다"로 바뀔 뿐이다.

### 1.3 파생된 버그 — 목록 참여자 수가 영구히 낡는다 ★

`app/polls/page.tsx`에 `export const revalidate`가 없다. 따라서 이 정적 페이지는 **`revalidatePath('/polls')` 호출로만** 갱신된다.

그걸 호출하는 곳을 전수 확인했다:

| 액션 | `/polls` 무효화 | 파일 |
|---|---|---|
| `createUserPoll` | O | `lib/actions/polls.ts:94` |
| `deleteUserPoll` | O | `lib/actions/polls.ts:141` |
| `submitVote` | **X** (`/polls/{id}`만) | `lib/actions/vote.ts:34,92` |
| `submitRatingVotes` | **X** (`/polls/{id}`만) | `lib/actions/ratings.ts:37,102` |

즉 **표를 아무리 던져도 목록의 `vote_count`는 빌드 시점 값에서 움직이지 않는다.** 누군가 새 투표를 만들 때 우연히 함께 갱신될 뿐이다.

성능 문제가 아니라 정확성 문제이고, 1차 4장의 1,000행 캡 버그와 성격이 같다 — **에러 없이 조용히 틀린 값을 보여준다.**

수정:

```ts
// app/polls/page.tsx
export const revalidate = 30   // 안쪽 getPollList의 unstable_cache(30)와 정렬
```

`/players`가 이미 `revalidate = 60`으로 같은 처리를 하고 있다. `/polls`만 빠져 있다.

## 2. `loading.tsx`가 프로젝트 전체에 0개다

`Suspense`는 `app/layout.tsx`의 OAuth 코드 핸들러 1곳뿐이고, `loading.tsx`는 하나도 없다.

결과적으로 모든 동적 페이지가 **서버에서 모든 쿼리를 끝낸 뒤에야 첫 바이트를 보낸다.** `/predictions/{weekKey}` 결과 화면 기준:

```
요청 -> getFixtureWeeks (캐시)
     -> getPickCandidates (캐시) + getMyPredictions      [병렬]
     -> getMyResults + getWeekRanking                    [병렬]
     -> 전부 완료된 뒤 첫 바이트
```

랭킹 view 재계산이 느리면 **헤더 한 줄까지 같이 늦는다.** 그 사이 사용자는 빈 화면을 본다.

`loading.tsx` 3개를 추가하면 페이지 셸이 쿼리와 무관하게 즉시 나간다:

```
app/predictions/loading.tsx
app/predictions/[weekKey]/loading.tsx
app/polls/[id]/loading.tsx
```

**DB를 한 줄도 건드리지 않는 개선**이며 체감 변화가 가장 크다.

### 주의 — 이건 k6로 재면 "효과 없음"이 나온다

TTFB는 개선되지만 **문서가 보는 지표(전체 응답 p95)는 거의 안 움직인다.** 비교실험 설계서 2장이 실험 C를 지연 측정에서 제외한 것과 같은 이유다. A/B 표에 넣지 말고 별도로 다룬다.

랭킹처럼 느린 부분만 `<Suspense>`로 감싸 나머지를 먼저 흘려보내는 방식도 가능하지만, `loading.tsx`부터 넣고 효과를 확인한 뒤 판단한다.

## 3. 랭킹 쿼리가 캐시를 못 붙이는 원인 ★

비교실험 설계서 실험 A(P0-2)는 "랭킹 view에 `unstable_cache`를 붙인다"인데, **현재 구조로는 붙일 수 없다.** 원인을 코드에서 특정했다.

```ts
// lib/queries/predictions.ts:136  getWeekRanking
const { data: { user } } = await supabase.auth.getUser()          // <- 원인
const { data } = await supabase.from('week_leaderboard')...
return data.map(row => ({ ..., isMe: row.user_id === user?.id })) // <- 사용자별 값 혼입
```

`week_leaderboard` / `season_leaderboard` 조회 자체는 **완전한 공개 데이터**다. `user`를 읽는 유일한 이유는 `isMe` 불리언 하나를 붙이기 위해서다. 그런데 반환값에 사용자별 정보가 섞이는 순간 캐시가 불가능해진다 — 캐시하면 남의 `isMe`가 보인다.

### 수정 방향 — 공개 부분만 캐시하고 개인화는 캐시 밖에서

```ts
const getWeekRankingCached = unstable_cache(
  async (weekKey: string) => { /* getUser 없이 view만 조회 */ },
  ['week-ranking'],
  { revalidate: 60, tags: ['ranking'] }
)

export async function getWeekRanking(weekKey: string, userId: string | null) {
  const rows = await getWeekRankingCached(weekKey)
  return rows.map(r => ({ ...r, isMe: r.userId === userId }))
}
```

`getSeasonRanking`(`predictions.ts:169`)도 동일 구조라 같은 수정이 적용된다.

### 이 수정 하나가 실험 A와 실험 C를 동시에 만족시킨다

| 얻는 것 | 대응 실험 |
|---|---|
| view 재계산이 60초 1회로 감소 | **실험 A** (P0-2) |
| `auth.getUser()` 왕복 1개 제거 | **실험 C** (P1-7) |

→ **비교실험 설계서 2장의 A/C 분리는 재검토가 필요하다.** 두 실험이 같은 코드 변경을 대상으로 하므로, 개선 브랜치를 하나만 만들어도 두 지표가 함께 움직인다.

### `auth.getUser()` 호출 수 실측

| 페이지 | 호출 수 | 내역 |
|---|---|---|
| `/predictions` | 2회 | `getMyPredictions`, `getSeasonRanking` |
| `/predictions/{weekKey}` 결과 화면 | **3회** | `getMyPredictions`, `getMyResults`, `getWeekRanking` |

설계서 2장의 "3회에서 1회"가 이 경로다. `Promise.all` 병렬이라 지연은 거의 안 줄고 Auth 호출량만 줄어든다는 설계서 판단은 실측과 일치한다.

## 4. `/polls/{id}`는 캐시가 하나도 없다

`getPollById`(`queries/polls.ts:261`)는 제목·설명·선택지·선수 정보 등 **거의 변하지 않는 공개 데이터**를 조인으로 읽는데 캐시가 없다. 요청마다 나간다.

무효화 훅은 이미 전부 깔려 있다 — `actions/vote.ts`, `ratings.ts`, `comments.ts`가 모두 `revalidatePath('/polls/{pollId}')`를 호출한다. 다만 이건 **경로 전체를 날리는** 방식이라 댓글 하나 달릴 때 투표 본문 캐시까지 함께 버려진다. 태그를 쪼개면(`poll-{id}` / `comments-{id}`) 필요한 것만 무효화할 수 있다.

**우선순위는 낮다.** 현재 실데이터가 50건대라 체감 차이가 없고, 태그 분리는 무효화를 놓쳤을 때 **낡은 데이터가 표시되는** 방향으로 깨진다. 3장을 먼저 처리하고 나중에 온다.

## 5. `next/image` 미사용 — 죽은 설정

```
<img>       20곳 (12개 파일)
next/image   0곳
```

그런데 `next.config.mjs`에는 `images.remotePatterns`가 3개(`placehold.co`, `*.supabase.co`, `lh3.googleusercontent.com`) 선언돼 있다. **한 번도 쓰이지 않는 설정이다.**

`npm run build`도 `@next/next/no-img-element` 경고를 낸다. `next/image`로 바꾸면 자동 리사이즈·WebP 변환·lazy loading이 붙는다.

단 Vercel의 이미지 최적화는 **과금 대상**이므로 전면 교체는 하지 않는다. LCP에 잡히는 이미지(선수 사진, 투표 썸네일) 몇 개만 우선 교체한다.

관련 파일: `PollCard.tsx`, `PlayersPageClient.tsx`, `RankingCard.tsx`, `WeekRankCard.tsx`, `predict/shared.tsx` 외 7개.

## 6. 우선순위

| 순위 | 작업 | 비용 | 효과 | 성격 |
|---|---|---|---|---|
| 1 | `app/polls/page.tsx`에 `revalidate = 30` | **1줄** | 목록 참여자 수 stale 해결 | **버그 수정** |
| 2 | `loading.tsx` 3개 추가 | 파일 3개 | 체감 속도. DB 무관 | 렌더링 |
| 3 | 랭킹 쿼리에서 `isMe` 분리 후 캐시 | 함수 2개 | view 재계산 제거 + Auth 왕복 감소 | **실험 A + C 통합** |
| 4 | `getPollById` 캐시 + 태그 분리 | 함수 1개 | 성장 시에만 유효 | 캐싱 |
| 5 | LCP 이미지만 `next/image` | 파일 2~3개 | Lighthouse | 렌더링 |

- **1번은 성능이 아니라 버그다.** 측정 대상이 아니며 지금 고치는 게 맞다.
- **2번은 k6 A/B 표에 넣지 않는다** (2장 주의).
- **3번이 A/B 측정 값어치가 있는 유일한 항목이다.**
