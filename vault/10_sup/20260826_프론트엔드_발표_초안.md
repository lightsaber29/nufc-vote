# 프론트엔드 발표 초안 — "언제 가져오느냐"가 초기 화면을 결정한다

- 작성일: 2026-08-26
- 대상: NUFC 팬 투표 플랫폼 (Next.js 14 App Router + Supabase, Vercel)
- 발표 길이 가정: 10~12분 (슬라이드 9장 + Q&A)

---

## 0. 발표 한 줄 주장

> **"Supabase가 느리다"가 아니라, Supabase 데이터를 *언제* 가져오느냐가 초기 화면 성능을 결정한다.**

문제를 "DB가 느림"으로 잡으면 인덱스·쿼리 튜닝으로 가지만, "가져오는 시점"으로 잡으면
렌더링 위치(클라이언트 → 서버)와 캐싱이 답이 된다. 이 발표는 후자를 택한 이유와 그 결과다.

---

## 1. Before — 데이터가 화면보다 세 걸음 늦게 출발한다

```
브라우저: HTML 수신 → JS 번들 다운로드 → React 실행 → useEffect
                                                        ↓
                                              여기서야 Supabase 요청 시작
                                                        ↓
                                                  데이터 도착 → 화면
```

핵심은 **직렬**이라는 것. 사용자는 이미 화면을 보고 있는데 그 화면은 비어 있고,
요청은 JS가 다 실행된 뒤에야 출발한다. 모바일·저사양 기기일수록 JS 실행 구간이 길어져
"데이터 요청 시작 시점" 자체가 뒤로 밀린다.

**말할 포인트**: 이 구조에서 Supabase 쿼리를 아무리 빠르게 만들어도, 사용자가 체감하는
빈 화면 시간은 거의 줄지 않는다. 병목이 쿼리가 아니라 **출발선**에 있기 때문.

---

## 2. After — 데이터를 HTML보다 먼저 가져온다

```
사용자 요청
  ↓
Next.js 서버 (Vercel)
  ↓ Supabase 조회 (서버에서, 병렬)
  ↓ 데이터 획득
  ↓ HTML/RSC 생성
브라우저 수신 → 화면 표시(이미 데이터가 채워져 있음) → HomeClient hydration
```

코드 (`frontend/src/app/page.tsx`):

```tsx
export const revalidate = 30

export default async function HomePage() {
  const [sections, fixture] = await Promise.all([
    getPollHomeSections(),
    getHomeMatchdayFixture(),
  ])
  return <HomeClient sections={sections} fixture={fixture} />
}
```

바뀐 것: 요청 시작점이 "브라우저의 JS 실행 이후"에서 "서버가 HTML을 만들기 전"으로 이동.
사용자가 첫 바이트를 받는 순간 이미 투표 목록이 들어 있다.

**단, 공짜가 아니다.** 조회가 서버로 옮겨온 만큼 **그 시간이 TTFB에 그대로 들어간다.**
그래서 다음 슬라이드가 필요하다.

---

## 3. 그래서 캐싱 — TTFB를 방어하는 장치

`unstable_cache`로 조회 결과 자체를 Next 서버에 캐싱한다. 데이터 성격에 따라 TTL을 나눴다.

| 데이터 | TTL | 파일 | 근거 |
|---|---|---|---|
| 홈 투표 섹션 / 투표 목록 | 30초 | `lib/queries/polls.ts:263,340` | 참여 수가 계속 변함 — 최신성 우선 |
| 홈 경기 정보 | 30초 | `lib/queries/fixtures.ts:247` | 홈 라우트 `revalidate=30`과 정렬 |
| 예측 랭킹 | 60초 | `lib/queries/predictions.ts:151,192` | 집계값, 초 단위 최신성 불필요 |
| 경기 주차 / 평점 변동 | 300초 | `fixtures.ts:278`, `player-pick-one.ts:81` | 하루 단위로 바뀜 |
| 선수 후보 명단 | 3600초 | `lib/queries/squads.ts:92` | 사실상 시즌 단위 고정 |

라우트의 `export const revalidate = 30`과 안쪽 `unstable_cache(30)`을 **같이** 건 이유:
라우트 쪽이 없으면 정적 라우트로 굳어 참여자 수가 빌드 시점 값에 멈춘다.
(코드 주석으로 남겨 둠 — `page.tsx:6`)

**캐싱하지 않은 것도 설계다**: 내 예측 제출 내역은 사용자별 데이터라 캐시에서 제외했다
(`predictions.ts:48`). 캐시가 남의 예측을 보여주면 성능이 아니라 사고다.

**이 정책은 테스트로 고정**했다 — `lib/queries/cache-policy.test.mjs`가
공개 쿼리 모듈에 `unstable_cache`가 살아 있는지 검사한다. 리팩터링하다 캐싱이 조용히
빠지는 걸 막기 위함.

## 4. 조회 자체를 줄인 두 가지

### (1) 병렬 — Promise.all

서로 의존하지 않는 조회는 순차로 기다릴 이유가 없다. 홈은 `getPollHomeSections`와
`getHomeMatchdayFixture`를 동시에 발사한다. 내부에서도 마찬가지로,
생성자 이름 조회와 평점 참여자 수 조회를 병렬로 묶었다 (`polls.ts:200~205`).
→ 서버 조회 구간의 지연이 **합**이 아니라 **최댓값**이 된다.

### (2) 화면에 보이는 만큼만 SQL로

홈 캐러셀은 "미리보기"지 전체 목록이 아니다. 전량을 가져와 JS에서 자르는 대신
SQL 단계에서 상한을 건다 (`polls.ts`):

```ts
const HOME_SECTION_ITEM_LIMIT = 8    // 섹션(진행중/예정/종료)당 노출 개수
const HOME_SECTION_FETCH_LIMIT = 60  // 버킷 분류를 위해 훑을 최근 투표 수
```

전체 목록은 `/polls`의 전체보기로 넘긴다. 홈이 커진다고 홈 쿼리가 같이 커지지 않는 구조.

### (덤) 불필요한 선반입 차단
`prefetch={false}`로 하단 네비게이션과 투표 카드 링크의 RSC payload 선반입을 껐다.
카드가 화면에 스무 개 있으면 프리페치도 스무 번 나간다 — 초기 화면을 위한 대역폭을
목록 스크롤이 먹는 걸 막았다. (`prefetch-policy.test.mjs`로 고정)

## 5. 이미지 — 이미 들어 있는 걸 쓴다

`next/image`가 표시 크기에 맞춰 서버에서 리사이즈하고 WebP/AVIF로 변환해 준다.
추가 라이브러리 없이 표시 크기 + 포맷 두 축을 동시에 줄인다.

여기에 더해 **업로드 시점**에도 한 번 줄인다 (`lib/images/optimize.ts`, sharp):

| 프리셋 | 폭 | 품질 |
|---|---|---|
| general / poll-thumbnail | 1280 | 72 |
| player-photo | 720 | 72 |
| poll-option | 1000 | 70 |

`poll-option`만 1000px인 건 크롭 UI가 1000×1300으로 잘라 보내기 때문 —
720으로 줄이면 약속한 해상도가 깨진다. 전부 `.webp`로 저장.

## 6. 측정 — 실제로 움직였나 (Lighthouse, 모바일 4x CPU 스로틀)

| 지표 | 1차 | 2차 | 3차 | 4차(2026-08-26) |
|---|---|---|---|---|
| Performance | 55 | 73 | 80 | **77** |
| LCP | — | 14.4s | 4.89s | **5.39s** |
| TTI | — | 14.5s | 5.18s | **5.45s** |
| TBT | — | 2ms | 18ms | **3ms** |
| CLS | — | 0 | 0.0001 | **0.0002** |
| 서버 응답 | — | — | 10ms | **10ms** |

**말할 포인트 1 — 가장 큰 변화는 LCP 14.4s → 4.9s (≈ -66%).** 이게 1~4번 작업의 결과다.

**말할 포인트 2 — 서버 응답 10ms.** 조회를 서버로 옮겼는데도 TTFB가 낮은 건
캐싱이 실제로 방어하고 있다는 증거다. "서버로 옮기면 TTFB가 늦어진다"는 우려에 대한 답.

**말할 포인트 3 — 3차 80 → 4차 77로 내려갔다.** 이건 숨기지 않고 그대로 말한다.
측정 조건은 동일했고, 원인은 아래 7번이다.

## 7. 남은 문제 (숨기지 않는다)

1. **Hydration mismatch** — React #418/#423/#425 콘솔 에러 6건이 3차·4차에서
   청크 해시까지 동일하게 남아 있다. SSR HTML을 버리고 root 전체를 클라이언트에서
   다시 그리는 상태(#423). **서버 렌더링의 이점을 일부 반납하고 있다** — 지금 최우선 과제.
2. **Cache-Control 회귀** — 외부(fotmob) 이미지를 Supabase Storage로 이전하면서
   팀 로고의 캐시 수명 7일 → 0이 됐다. 재방문마다 히어로 상단 30KB를 다시 받는다.
   조치는 확정: Storage 객체 메타데이터 일괄 갱신 (일회성 스크립트, `scripts/` 작업 중).
3. **Best Practices 96은 안정적인 점수가 아니다** — 서드파티 쿠키가 사라진 부수효과이고,
   Mixpanel이 다시 발사되면 되돌아온다.

## 8. 정리 — 무엇을 배웠나

1. **성능 문제는 "무엇이 느린가"보다 "어디서 시작하는가"를 먼저 본다.**
   같은 Supabase 쿼리인데 시작 시점만 옮겨서 LCP가 3분의 1이 됐다.
2. **최적화는 트레이드오프다.** 조회를 서버로 옮기면 TTFB로 청구서가 온다.
   캐싱은 그 청구서를 막는 짝이지, 별개 작업이 아니다.
3. **정책은 테스트로 고정한다.** 캐싱·프리페치 정책은 눈에 안 보여서 리팩터링에
   조용히 지워진다. `cache-policy.test.mjs` / `prefetch-policy.test.mjs`가 그걸 막는다.
4. **측정하지 않으면 개선했다고 말할 수 없다.** 4차에서 점수가 내려간 것도,
   내려간 이유를 지목할 수 있는 것도 매번 같은 조건으로 측정했기 때문이다.

## 예상 Q&A

**Q. 30초 캐시면 투표하고 새로고침했을 때 반영이 안 되는 것 아닌가?**
A. 투표 제출(`submitVote` / `submitRatingVotes`)은 `/polls/{id}` 상세를 무효화한다.
   내가 방금 한 행동의 결과는 즉시 보이고, 홈 캐러셀의 집계 숫자만 최대 30초 지연된다.
   (한계: 홈은 무효화 대상이 아님 — 의도된 선택.)

**Q. 왜 SSG(정적 생성)가 아니라 ISR인가?**
A. 참여자 수가 계속 변하는 화면이라 빌드 시점 값에 굳으면 안 된다. 실제로 라우트에
   `revalidate`를 안 걸었을 때 정적으로 굳는 문제를 겪었다.

**Q. 서버 컴포넌트로 옮기면 클라이언트 상호작용은?**
A. 데이터 조회만 서버(`page.tsx`)에 두고, 상호작용은 `HomeClient`로 내려 props로 받는다.
   "껍데기는 서버, 상태는 클라이언트" 경계.

**Q. Supabase 쿼리 자체는 튜닝 안 했나?**
A. 했다 — 필요한 컬럼만 select, SQL 단계 limit, 참여자 수 집계 분리.
   다만 이 발표의 주장은 "그것만으로는 초기 화면이 안 빨라진다"는 것.
