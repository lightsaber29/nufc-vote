## 1. 문제 — 잴 대상이 없다

성능을 개선하려면 먼저 느려야 한다. 그런데 이 서비스는 느릴 수가 없었다.

prod 실측(`20260821_백엔드_성능테스트_결과_분석.md` 4.5):

| 대상 | 실제 규모 |
|---|---|
| poll별 최대 표 수 | 1,000건 미만 |
| poll별 최대 평점 수 | **52건** |
| `rating_votes` 전체 | **52건** |

**52행짜리 테이블은 무엇을 어떻게 짜도 빠르다.** 인덱스를 붙여도, 집계를 DB로 내려도, 캐시를 붙여도 차이가 측정 한계 아래다.

그래서 부하 테스트의 질문을 바꿔야 했다.

| | 흔한 질문 | 이 서비스에서 가능한 질문 |
|---|---|---|
| 묻는 것 | "지금 어디가 느린가" | **"목표 규모에서도 맞게 동작하는가"** |
| 전제 | 트래픽이 있다 | 트래픽이 없다 |
| 종료 조건 | 병목 제거 | **목표 규모 시나리오 통과** |

### 1.1 그런데 1차 측정은 10만 표로 했다 — 그게 문제였다

1차(8/21)는 유저 10만 명 / 표 10만 개로 시드했다. 결함은 나왔지만 **prod의 약 2,000배**였다.

> 이 수치로 "성능을 개선했다"고 말하려면 규모 전제를 같이 밝혀야 하고, 안 밝히면 과장이다.
> — `20260824_포트폴리오_서사_정립.md` 9장

10만 표는 "언젠가 이런 일이 생길 수도 있다"까지만 말할 수 있다. **"지금 이걸 고쳐야 한다"는 말은 못 한다.**

## 2. 접근 — 목표 규모를 근거 있게 고정한다

임의의 큰 숫자 대신, **서비스 목표에서 규모를 유도**했다.

```
목표: 서비스 사용자 100명 (DAU)
  × 운영 중인 투표 10개
  × 1인 1투표 (DB UNIQUE 제약이 강제)
  = 1,000표
```

이 숫자는 마케팅 목표에서 나온 것이지 부하 테스트를 위해 지어낸 것이 아니다. **틀렸다면 사업 목표가 틀린 것이지 측정이 틀린 것이 아니다** — 이게 규모에 근거를 부여하는 방식이다.

### 2.1 투표 유형 구성

이 서비스의 투표는 두 종류이고, **같은 "1인 1표"인데 저장되는 행 수가 다르다.**

| 유형 | DB type | 제출 1회당 행 수 | 근거 |
|---|---|---|---|
| 선택형 | `selection` | `votes` **1행** | `UNIQUE(poll_id, user_id)` |
| 평점형 | `overall_rating` | `rating_votes` **선수 수만큼** | `lib/actions/ratings.ts:75`, `UNIQUE(poll_id, user_id, target_player_id)` |

선발+교체 14명을 평가 대상으로 잡으면:

```
선택형 5개 : 100명 × 5              =   500행  (poll당   100행)
평점형 5개 : 100명 × 14선수 × 5     = 7,000행  (poll당 1,400행)
```

> **같은 "사용자 100명"인데 한쪽은 100행, 다른 쪽은 1,400행이다.**
> 사용자 수만 보고 규모를 가늠하면 14배를 놓친다. 이게 이번 측정의 첫 발견이다.

### 2.2 부하 시나리오 — DAU를 초당 요청으로 옮기기

DAU 100명은 그 자체로 부하가 아니다. **언제 몰리는가**가 부하다. 두 가정을 모두 측정했다.

| 조건 | 가정 | 도착률 | 근거 |
|---|---|---|---|
| **A. 현실 피크** | 경기 종료 직후 5분에 DAU 100명 전원 유입 | **0.33 세션/s** (100명 / 300초) | 축구 팬 서비스에서 가장 방어 가능한 최악의 순간 |
| **B. 비현실 상한** | 100명이 같은 순간에 화면을 보고 있음 | VU 100 램프 | DAU 100에서 동시 100은 과장 — 상한으로만 읽는다 |
| **C. 포화점** | 서버가 무너지는 지점 | 20 → 400 iter/s | 여유가 몇 배인지 알려면 천장을 알아야 한다 |

1세션 = 목록 + 선택형 상세 + 평점형 상세 = **3 페이지뷰**.

## 3. 트래픽 만들기 — 재현 가능하게

### 3.1 시드

`scripts/seed-target-scale.mjs` (신규). 로컬에 `psql`·`supabase` CLI·DB 비밀번호가 없어 **PostgREST(service_role)로 직접 넣는다** — 새 도구 설치 0개.

```
users            100  (+ 실제 Auth 테스트 계정 5개는 보존)
players           14
polls             10  (selection 5 + overall_rating 5)
poll_options      95  (선택형 5×5 + 평점형 5×14)
votes            500
rating_votes   7,000
```

재현성을 위해 지킨 것 두 가지:

- **`random()` 금지.** 선택지 배정은 `ui % 선택지수`, 점수는 `(선수순번 + 사용자순번) % 6`으로 결정적이다. 1차 시드는 `ORDER BY random() LIMIT 1` 상관 서브쿼리가 한 번만 평가돼 **10만 표가 전부 한 선택지에 몰렸다** — 같은 실수를 반복하지 않는다.
- **staging 가드.** 스크립트 상단에서 `SUPA_URL`에 staging ref가 없으면 즉시 중단한다. prod에 실행되면 기존 데이터를 지우기 때문이다.

### 3.2 부하

`scripts/k6-load-test.js`에 두 가지만 더했다. 기존 모드는 건드리지 않았다.

| 추가 | 이유 |
|---|---|
| `RATING_POLL_ID` / `detail-rating` 태그 | 선택형과 평점형은 상세 경로의 행 수 증가율이 14배 다르다. 합치면 희석된다 |
| `TIME_UNIT` env | 0.33 iter/s 같은 소수 도착률을 표현해야 한다 (`RATE=1 TIME_UNIT=3s`) |

엔드포인트를 태그로 나누는 건 1차의 교훈이다 — 캐시된 목록(3.62ms)과 비캐시 상세(290ms)를 합치면 **80배 차이가 사라진다.**

| `/polls/{id}` 평점형 상세 | **155.33 ms** | 130.79 ms | 128.90 ms |

에러율 **0.00%** (303 요청). 목록이 빠른 건 빌드 시점 정적 생성(`○ Static`) 때문이고, 상세는 매 요청 DB를 친다.

> **목표 규모의 현실 피크에서 p95는 전부 200ms 미만이다.** 개선할 성능이 없다.

### 4.4 여유 계산 — 확장성 주장의 근거

```

안정 처리 확인      25.47 세션/s   (조건 B, 에러 0%, p95 0.8s)

여유                  약 77배
```

DAU 100명 목표 기준으로 **DAU 약 7,700명까지는 현재 구조 그대로 감당한다.** 인덱스도, 캐시도, RPC도 없이.

이것이 `20260824_백엔드_성능개선_점검.md` P2-1이 **인덱스 9개를 지금 붙이지 않기로 판단한 근거**를 실측으로 뒷받침한다.

### 4.5 그런데 에러율이 끝까지 0%다 — 이게 좋은 소식이 아니다

조건 C에서 평점형 상세가 **p95 5.58초**인데 **에러율은 0.00%**다. 서버가 요청을 거절하지 않고 전부 받아 줄을 세운다.

> **5xx만 모니터링하면 이 상태를 탐지할 수 없다.** 사용자는 5초를 기다리는데 알람은 울리지 않는다.

1차(3.1)에서 10만 표 규모로 관찰한 특성이 **목표 규모에서도 동일하게 나타났다.** 규모와 무관한 구조적 성질이다.

## 5. 결과 ② 정확성 — 목표 규모에서 이미 깨진다 ★

성능은 여유였다. 대신 **화면에 틀린 숫자가 떴다.**

### 5.1 화면 실측

목표 규모를 시드한 뒤 `/polls` 목록 페이지를 실제로 렌더한 결과:

| 투표 | 화면 표시 참여자 | 정답 |
|---|---|---|
| [TARGET] 이주의 선수 1~5R (선택형) | 100 / 100 / 100 / 100 / 100 | 100 |
| **[TARGET] 경기 평점 1~5R (평점형)** | **0 / 0 / 0 / 0 / 72** | **각 100** |

**평점 투표 참여 500건이 화면에는 72건으로 나온다.** 투표 5개 중 4개는 "아무도 참여하지 않음"으로 표시된다.

### 5.2 원인 — PostgREST `db-max-rows` 기본값 1,000

`lib/queries/polls.ts:96` `getRatingParticipantCounts`는 목록 한 페이지의 평점 투표를 **한 번에 모아 조회**한 뒤 JS `Set`으로 중복을 제거한다.

```ts
.from('rating_votes')
.select('poll_id, user_id')
.in('poll_id', pollIds)     // ← range/limit 없음
```

PostgREST에 직접 물어본 결과:

```
GET /rest/v1/rating_votes?select=poll_id,user_id&poll_id=in.(평점 poll 5개)
→ HTTP 200
   Content-Range: 0-999/7000      ← 7,000행 중 1,000행만
   103 KB
```

`PAGE_SIZE = 10`(`lib/constants.ts:2`)이라 투표 10개가 전부 1페이지에 올라온다. 즉 **평점 투표 5개가 1,000행 한도를 나눠 쓰다가 1개에서 소진된다.**

### 5.3 세 경로의 판정

| 경로 | 함수 | 실제 행 | 수신 행 | 판정 |
|---|---|---|---|---|
| 목록 참여자 수 | `getRatingParticipantCounts` (`polls.ts:87`, 쿼리 96행) | 7,000 | **1,000** | **깨짐** — 5개 중 1개만 인식, 그것도 72명 |
| 평점 상세 | `getRatingResults` (`polls.ts:471`, 쿼리 487행) | 1,400 | **1,000** | **깨짐** — 선수별 72/71개 (정답 100) |
| 선택형 득표 | `getVoteCounts` (`polls.ts:423`, 쿼리 430행) | 100 | 100 | **정상** (대조군) |

세 번째 줄이 중요하다. **같은 코드베이스, 같은 사용자 100명인데 한쪽만 깨진다.** 차이는 유형당 행 증폭률(1배 vs 14배)뿐이다.

### 5.4 왜 지금까지 발견되지 않았나

- **에러가 아니다.** HTTP 200, `error` 필드 없음, 정상 배열. 예외도 로그도 없다
- **작은 데이터에서는 맞는다.** prod 현재 52건에서는 정확하다
- **정적 페이지에 굳는다.** `/polls`는 빌드 산출물에서 `○ (Static)`이다 — 잘린 집계가 빌드 시점에 고정돼 그대로 서빙된다

### 5.5 임계값이 언제 오는가

```
평점 투표 참여자 = 1,000행 ÷ (평가 대상 선수 수) ÷ (목록 1페이지의 평점 투표 수)
```

| 선수 수 | 목록 평점 투표 1개 | 5개 |
|---|---|---|
| 11명 | 90명에서 깨짐 | **18명에서 깨짐** |
| 14명 | 71명 | **14명** |
| 25명 | 40명 | **8명** |

> **선수 14명 기준, 목록에 평점 투표 5개가 있으면 참여자 14명에서 이미 틀린다.**
> "사용자 100명"은커녕 **지인 테스트 규모에서 넘는다.** prod가 아직 안 걸린 건 평점 투표 자체가 적어서다.

| 예측/랭킹 경로 미측정 | `fixtures` 시드가 없어 `SUITE=polls`로만 측정했다 |

## 7. 결론

### 7.1 "트래픽이 없는데 어떻게 측정하나"에 대한 답

**목표에서 규모를 유도하고, 그 규모를 데이터로 만든다.**

임의의 10만 표는 "언젠가 이럴 수도 있다"까지만 말한다. 사업 목표에서 나온 1,000표는 **"지금 이걸 고쳐야 한다"**를 말할 수 있다. 같은 부하 테스트인데 결론의 힘이 다르다.

### 7.2 결과

| | 예상 | 실측 |
|---|---|---|
| 성능 | 병목을 찾을 것 | **여유 77배 — 고칠 것이 없다** |
| 정확성 | 문제 없음 | **목표 규모에서 이미 깨져 있다** |

부하 테스트가 성능 문제를 못 찾은 건 테스트가 부실해서가 아니라 **문제가 없어서**다. 그리고 이 규모에서 부하를 걸면 대신 나오는 게 있었다 — **작을 땐 맞는데 커지면 틀리는 전제**다.

### 7.3 발견의 성격

찾은 결함은 전부 **에러를 내지 않는다.**

| 겉보기 | 실제 |
|---|---|
| HTTP 200, 정상 배열 | 집계가 틀림 (5.2) |
| 화면에 "0명" | 100명이 참여했음 (5.1) |
| 에러율 0% | 사용자는 5.58초 대기 (4.5) |

로그도 없고 알람도 안 울리고 화면은 멀쩡하다. **부하 테스트를 하지 않았다면 발견되지 않았을 것이다.**
