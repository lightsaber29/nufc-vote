## 0. 왜 갱신이 필요한가 — 기존 스크립트와 실측이 어긋나 있다

기존 스크립트(11:48 작성)가 참조하는 수치는 **4차(09:31)** 기준이다. 그런데 5차(10:48)에서 그 스크립트가
"남은 과제"로 지목한 항목이 **이미 닫혔다.**

| 항목 | 기존 스크립트 | 실측 최신 | 근거 |
|---|---|---|---|
| Performance | 4차 77 | **89** | 5차 §1 |
| LCP | 14.4s → 4.89s | 14.4s → 4.89s → **2.95s** | 5차 §1 |
| FCP | 2.42s | **1.16s** | 5차 §1 |
| 서버 응답 | 10ms | **21ms** | 5차 §1 |
| Hydration mismatch | 남은 과제 · 최우선 | **에러 6건 → 0건 (해결)** | 5차 §2① |
| Cache-Control 회귀 | 남은 과제 | **절감 여지 86KB → 2KB (해결)** | 5차 §2② |
| 참여자 집계 서버 전환 | 남은 과제 | **뷰 전환 완료 · 재실측 통과** | 코드수정 리스트업 A-1 |

> **즉 기존 8번 슬라이드의 「남은 과제」 3개가 전부 닫혔다.** 이 슬라이드를 그대로 띄우면
> "아직 안 고쳤다"고 말하게 된다. 갱신 대상은 **표지 · 3장 · 6장 · 7장**이고, 나머지 4장(1·2·4·5)은 손대지 않는다.

### 서사에 미치는 영향

발표의 뼈대(`① → 다리 → ② → 반전`)는 **바꾸지 않는다.** 다만 마지막 두 장의 무게가 이동한다.

- 기존: "찾았다. 남은 과제 3개."
- 갱신: "**찾아서 고쳤다. 고치니 가려져 있던 게 드러났다.**" (CLS·TBT는 hydration을 고쳐서 *보이게 된* 항목이다 — 5차 §3·§4)

## 슬라이드 2: ① 문제는 쿼리가 아니라 출발선

- **핵심 메시지:** 병목은 쿼리가 아니라 요청이 출발하는 시점에 있었다.
- **본문:**
  - Before — `HTML 수신 → JS 번들 → React 실행/useEffect → 여기서야 Supabase 요청`
  - After — `서버에서 Supabase 조회(병렬) → HTML/RSC 생성 → 브라우저는 이미 채워진 화면 수신 → hydration`
  - 캡션: 번들 다운로드는 HTML 파싱 중 시작되지만 **데이터 요청은 직렬**이다
- **시각 자료 제안:** 기존 좌우 2단 흐름도 유지. **변경 없음.** (`page.tsx` 코드는 넣지 않는다 — 5분에서 코드를 읽히면 20초가 날아간다.)
- **발표 스크립트:**
  > 원래는 HTML을 받고, 번들을 내려받고, React가 실행된 뒤에야 `useEffect`에서 Supabase 요청이 출발했습니다.
  > **데이터 요청 기준으로 직렬**입니다. 사용자는 이미 화면을 보고 있는데 그 화면이 비어 있어요.
  > 이 구조에서는 **쿼리를 아무리 빠르게 만들어도** 빈 화면 시간이 안 줄어듭니다. 병목이 쿼리가 아니라 **출발선**에 있으니까요.
  > 그래서 조회를 서버 컴포넌트로 올렸습니다. 서버가 HTML을 만들기 **전에** Supabase를 치고, 의존 없는 조회는 `Promise.all`로 같이 발사합니다.

  *("데이터 요청 기준으로"라는 한정어를 빼지 않는다. 붉은 박스에서 한 박자 쉰다.)*

## 슬라이드 3: ① 캐싱은 별개 작업이 아니라 짝 ★갱신

- **핵심 메시지:** 조회를 서버로 옮긴 비용은 TTFB로 청구되고, TTL 정책이 그 청구서를 막는다.
- **본문:**
  - TTL 3행만 — 홈/목록 `30초` · 선수 후보 명단 `3600초` · **내 예측 제출 내역 `캐시 제외`**(사용자별 데이터)
  - **LCP 사다리** `14.4s → 4.89s → 2.95s`
  - **서버 응답 21ms** — "서버로 옮기면 TTFB가 늦어진다"에 대한 답
  - 정책은 `cache-policy.test.mjs` / `prefetch-policy.test.mjs`로 고정
- **시각 자료 제안:**
  기존 우측의 **큰 숫자 박스 2개를 「사다리 차트」 1개 + 「서버 응답」 박스 1개로 교체**한다.
  단일 화살표(`14.4 → 4.9`)는 개선분이 전부 ①의 몫인 것처럼 읽히는데, 실제로는 두 단계다.

  ```
  LCP          14.4s ──────────> 4.89s ──────────> 2.95s
                     ① 렌더링·캐싱      hydration 수정
  Performance   73  ──────────>  80  ──────────>  89
                                        (4차 77은 hydration 재렌더 구간)
  ```

  - 형태: 가로 3점 라인 + 각 구간에 원인 라벨. 막대보다 라인이 "단계"를 보여주기에 적합.
  - 하단 캡션: `Lighthouse 모바일 · 4x CPU 스로틀 · 동일 조건 5회 측정`
- **발표 스크립트:**
  > 그런데 공짜가 아닙니다. 옮겨온 조회 시간이 **그대로 TTFB로 청구**됩니다. 그래서 데이터 성격에 따라 TTL을 나눴습니다.
  > 하나만 보시면, **내 예측 제출 내역은 캐시에서 뺐습니다.** 캐시가 남의 예측을 보여주면 성능이 아니라 사고니까요.
  > 결과는 LCP가 14.4초에서 4.89초. 여기까지가 ①번의 몫이고, **오늘 아침 hydration mismatch를 잡으면서 2.95초까지 내려왔습니다.**
  > 그리고 **서버 응답이 21밀리초**입니다. 캐싱이 TTFB를 방어하고 있다는 증거예요.

  *(TTL 숫자를 읽지 않는다 — 화면이 말한다. 구두는 "캐시 제외" 하나만.)*

## 슬라이드 4: 다리 — 그럼 그 캐시에 담긴 값은 맞는가

  - `/polls`는 **당시** 빌드 산출물에서 `○ (Static)` — `revalidate` 선언이 없었다

- **시각 자료 제안:** 텍스트 2줄짜리 전환 슬라이드. **변경 없음.** 이 한 장이 두 파트를 인과로 묶는다.
- **발표 스크립트:**
  > 여기까지가 ①번입니다. 그런데 ②번으로 가기 전에 걸리는 게 있었어요.
  > **그럼 그 캐시에 담긴 값은 맞는가?**
  > **당시** `/polls`는 빌드 산출물에서 Static이었습니다. `revalidate` 선언이 없어서요.
  > 이 구조는 맞는 값만 굳히는 게 아니라 **틀린 값도 똑같이 굳힙니다.** 그래서 ②번을 보러 갔습니다.

  *("당시"를 반드시 붙인다 — 3장에서 30초 TTL을 말한 직후라, 이 한 단어가 없으면 모순으로 들린다.)*

## 슬라이드 5: ② 트래픽이 0인 서비스에서 뭘 재나

- **핵심 메시지:** 임의의 큰 숫자 대신 서비스 목표에서 규모를 유도했다.
- **본문:**
  - `DAU 100명 × 운영 중인 투표 10개 × 1인 1표 = 1,000표`
  - 선택형 = `votes` **1행** / 평점형 = `rating_votes` **14행**(선수 수만큼)
  - 같은 "사용자 100명"인데 한쪽은 500행, 다른 쪽은 7,000행
- **시각 자료 제안:** 기존 그대로 — 상단 수식 밴드 1개 + 하단 좌우 카드 2개. **변경 없음.**
- **발표 스크립트:**
  > SQL을 최적화하려면 먼저 느려야 합니다. 그런데 평점 투표 테이블이 **52행**이에요. 52행짜리는 뭘 어떻게 짜도 빠릅니다.
  > 그래서 규모를 만들었습니다. 임의의 큰 숫자는 "언젠가"까지밖에 못 말해요. 그래서 **서비스 목표에서 유도**했습니다. 사용자 100명, 투표 10개, 1인 1표 — 1,000표.
  > 여기서 첫 발견이 나왔습니다. 같은 1인 1표인데 **선택형은 1행, 평점형은 선수 수만큼 14행**입니다. 사용자 수만 보고 규모를 가늠하면 **14배를 놓칩니다.**

## 슬라이드 6: ② 예상과 실측 ★★갱신 (발표의 정점)

- **핵심 메시지:** 성능은 77배 여유였고, 대신 에러 없이 틀린 값을 찾았다 — 그리고 고쳤다.
- **본문:**
  - **성능** — 예상: 병목을 찾을 것 / 실측: **77배 여유** (현실 피크 0.33 세션/s vs 안정 처리 25.47 세션/s, 에러율 0%)
  - **정확성** — 예상: 문제 없음 / 실측: **500 → 72** (HTTP 200 · 정상 배열 · 로그 없음)
  - 원인: Supabase `db-max-rows` = 1,000 (PostgREST 자체 기본값은 무제한)
  - 임계값: 선수 14명 · 목록에 평점 투표 5개면 **참여자 14명에서 이미 틀린다**
  - **[신규] 수정 결과** — `count(distinct user_id)` 뷰로 전환 → 같은 시드 재조회에서 **평점 투표 5개 전부 100**
- **시각 자료 제안:**
  기존 좌우 2카드(성능 / 정확성) + 하단 `원인 · 임계값 · 가정` 3행 구조를 유지하고,
  **맨 아래에 「수정」 1행을 추가**한다(기존 `가정` 행 아래, 라벨 폭·서체 동일하게).

  | 라벨 | 내용 |
  |---|---|
  | 수정 | `rating_poll_participants` 뷰 (`count(distinct user_id)`) → 응답이 poll당 1행이라 캡에 닿지 않음 · 동일 시드 재조회 **5개 poll 전부 100** (구방식: 1개 72 + 4개 누락) |

  - 우측 정확성 카드의 큰 숫자를 `500 → 72`에서 **`500 → 72 → 500`**으로 바꾸는 안도 있으나, **권장하지 않는다.**
    이 장의 힘은 "틀린 값을 찾았다"에 있고, 숫자 3단은 발견을 희석시킨다. 수정은 아래 1행으로 충분하다.
    *(이건 발표 효과에 대한 제 판단이지 사용자 목표에서 나온 게 아니다 — 뒤집어도 무방하다.)*
- **발표 스크립트:**
  > 이 규모로 부하를 걸었습니다. 두 칸 다 예상이 틀렸어요.
  > 먼저 성능. 병목을 찾을 줄 알았는데 **여유가 77배**였습니다. 현실 피크 초당 0.33세션인데 에러 없이 25세션을 처리합니다. **DB 인덱스 하나 없이요.** 그래서 **인덱스 9개를 지금 안 붙이기로** 했습니다.
  > 대신 다른 게 나왔습니다. 평점 투표 참여 **500건이 화면에 72건으로** 표시됩니다.
  > 원인은 **Supabase의 `db-max-rows` 1,000**입니다. 상한 없는 select가 조용히 잘려요. 에러가 아닙니다. HTTP 200에 정상 배열이고 로그도 안 남습니다.
  > 먼 얘기가 아닙니다. **목록에 평점 투표가 5개니까**, 선수 14명 기준 **참여자 14명에서 이미 틀립니다.** 지인 테스트 규모예요.
  > 이건 집계를 DB로 내려 고쳤습니다. **같은 시드로 재보니 다섯 개 전부 100입니다.**

## 슬라이드 7: 배운 것 ★★갱신 (남은 과제 영역 삭제)

- **핵심 메시지:** 측정하지 않으면 개선했다고도, 멀쩡하다고도 말할 수 없다.
- **본문:**
  - **배운 것 ①** 성능 문제는 "무엇이 느린가"보다 **"어디서 시작하는가"** — 같은 쿼리인데 시작 시점만 옮겨서 LCP가 1/3
  - **배운 것 ②** 최적화는 트레이드오프 — 캐싱은 그 **짝**이지 별개 작업이 아니다
  - **닫힌 과제** — `revalidate = 30` / hydration mismatch 6건 → 0 / `Cache-Control` 86KB → 2KB / 참여자 집계 뷰 전환
- **시각 자료 제안:**
  - 제목을 `배운 것 / 남은 과제` → **`배운 것`**으로 정정(남은 과제 카드가 없으므로).
  - 「배운 것」 2블록을 **전체 폭(10.9인치)으로 확장**. 중복된 소제목 라벨(`배운 것`)은 제목과 겹치므로 제거.
  - 하단의 `4장의 /polls Static은 이후 revalidate = 30으로 수정 완료` 한 줄 → **「닫힌 과제」 4개 목록**으로 교체
    (`✓ revalidate = 30  ✓ hydration mismatch  ✓ Cache-Control  ✓ 참여자 집계 뷰`).
    **이 한 줄이 이번 갱신의 실질적 성과 표시다.**
  - **우측 「남은 과제」 카드 일체 삭제** — 카드 배경 · 「남은 과제」 제목 · 불릿 3개 · 항목 3쌍(총 11개 도형).
- **발표 스크립트:**
  > 이 두 개 다, **부하를 걸어보기 전에는 몰랐습니다.** 거기서 남은 게 두 문장입니다.
  > 첫째, 성능 문제는 "무엇이 느린가"보다 **"어디서 시작하는가"**를 먼저 봤습니다. 같은 쿼리인데 시작 시점만 옮겨서 LCP가 1/3이 됐어요.
  > 둘째, 최적화는 트레이드오프입니다. **캐싱은 그 청구서를 막는 짝이지, 별개 작업이 아니었습니다.**
  > 아래 네 개는 이번 주에 닫은 것들입니다.
  > **측정하지 않으면 개선했다고도, 멀쩡하다고도 말할 수 없습니다.** 감사합니다.

  *(닫힌 과제 4개를 읽지 않는다 — 화면이 말한다. 마지막 문장을 "~것 같습니다"로 흐리지 않는다.)*

# 부록 A. Q&A 대비 (2분)

기존 스크립트의 Q&A 표를 그대로 쓰되, 갱신으로 **새로 생기는 질문 4개**를 추가한다.

| 질문 | 답의 뼈대 |
|---|---|
| **LCP가 4.89에서 2.95로 더 내려간 건 무슨 작업인가** | 날짜 포맷터 6곳에 `timeZone: 'Asia/Seoul'`을 고정한 것뿐이다. hydration mismatch로 root 전체가 CSR로 다시 그려지고 있었고, `elementRenderDelay`가 291ms → 45ms로 떨어졌다 |
| **왜 4차에서 80 → 77로 내려갔었나** | 같은 hydration 재렌더 구간이다. 숨기지 않고 4차 리포트에 그대로 적었고, 5차에서 원인이 실측으로 확인됐다 |
| **TBT가 3ms에서 265ms로 나빠졌는데** | 우리 코드가 무거워진 게 아니다. TBT는 FCP 이후 블로킹만 센다. FCP가 1.25초 앞당겨지면서 브라우저 확장 프로그램의 232ms 태스크가 측정 창 안으로 들어왔다. **사이트를 빠르게 만든 결과로 점수가 나빠진 것** — 그래서 시크릿 재측정이 1순위다 |
| **CLS 0.052는 이번 수정 때문 아닌가** | 원래 있던 문제가 드러난 것이다. 4차까지는 첫 페인트 자체가 마운트 이후라 카운트다운이 이미 들어 있었다. hydration을 고쳐 SSR HTML이 살아남자 카운트다운이 뒤늦게 나타나며 목록을 밀어낸다 |
| 4장에선 Static이라더니 3장 TTL 30초는 뭔가 | **시점이 다르다.** 당시 `app/polls/page.tsx`에 `revalidate` 선언이 없어 바깥 정적 라우트가 안쪽 `unstable_cache(30)`을 삼켰다. 지금은 `revalidate = 30`이 들어가 있다 |
| `db-max-rows` 1,000이 PostgREST 기본값인가 | **아니다.** PostgREST 자체 기본값은 무제한이고, 1,000은 Supabase 호스팅이 넣는 값이다 |
| 77배면 아무것도 안 해도 되나 | 목표 규모 기준이다. DAU 7,700까지. 그 위는 다시 재야 한다 |
| 0.33 세션/s는 어디서 나왔나 | **가정이다.** DAU 100명 전원이 경기 종료 직후 300초에 유입 — 100/300. 77배는 이 가정에 비례해 움직인다 |
| 에러율 0%면 괜찮은 것 아닌가 | 포화점에서 p95가 5.58초인데 에러율은 0%다. **5xx만 보면 이 상태는 안 잡힌다** |
| 그 ms 수치는 prod인가 | **아니다.** 부하 테스트는 로컬 프로덕션 빌드 → staging Supabase다. Vercel 콜드스타트·리전 지연 미반영 (Lighthouse 수치는 prod URL 실측) |
| 왜 10만 표로 안 하고 1,000표인가 | 10만은 prod의 2,000배다. "언젠가"까지만 말할 수 있고 "지금 고쳐야 한다"는 못 한다 |

**넘기지 않고 준비만 해두는 부록 슬라이드** (기존 목차 3절 그대로): 조건 A/B/C 결과 3표 · TTL 정책 전체 표 · 세 경로 판정 표 · 측정 한계 · 재현 절차.
