## 0. 로컬 전용 제약 — 무엇을 포기하고 무엇을 얻는가

측정 위치가 **로컬 → staging Supabase**로 고정된다. Vercel 함수 경로는 재지 않는다.

### 포기하는 것

| 항목 | 결과 |
|---|---|
| Vercel 콜드스타트·함수 동시성 | 미반영. 실사용자 지연은 이 값보다 크다 |
| Vercel → Supabase 리전 간 지연 | 미반영. 8/19 리전 변경 효과는 이 측정에 안 나타난다 |
| **절대값의 대표성** | 여기서 나온 ms는 **prod 지연이 아니다.** 조건 간 *차이*만 유효하다 |
| 부하 생성기 분리 | k6와 Next.js가 같은 머신 — 1차 한계 7장 첫 항목이 그대로 남는다 (→ 4장에서 부하 수준을 낮춰 완화) |

### 얻는 것 — 1차와 조건이 같아진다

1차 측정도 한계 7장 그대로 **로컬 → staging Supabase**였다. 6.2의 "왕복 1회당 약 28ms"는 이미 로컬 왕복 비용이다.

즉 로컬 측정은 차선책이 아니라 **1차 기준선과 직접 비교 가능한 유일한 조건**이다. Vercel preview로 옮기면 1차 수치와 나란히 놓을 수 없어 별도 기준선을 다시 떠야 한다.

### 반드시 기록해야 할 편향

로컬 → Supabase RTT는 Vercel → Supabase RTT보다 크다. 따라서 **왕복 수를 줄이는 개선(P1-6, P1-8)의 효과가 로컬에서 과대하게 나온다.** 방향은 맞지만 크기는 **상한값**으로 읽어야 한다. 실험 A(캐시)도 DB 왕복을 없애는 것이므로 같은 편향을 받는다.

반대로 **DB 실행시간 자체(랭킹 view 재계산)는 편향되지 않는다** — 계산은 Supabase에서 일어나므로 측정 위치와 무관하다. 실험 A의 핵심 근거는 이쪽이다.

## 1. 왜 다시 측정하는가 — 1차와 다른 점

1차(8/21)는 **병목을 찾는** 측정이었다. 이번은 **개선을 검증하는** 측정이므로 요구사항이 다르다.

| | 1차 | 이번 |
|---|---|---|
| 질문 | "어디가 느린가" | "이 수정이 실제로 빠르게 하는가" |
| 필요 조건 | 절대값 | **두 조건의 차이가 노이즈보다 큰가** |
| 최대 위험 | 병목 오판 | **노이즈를 개선으로 착각** |

1차 6.5가 규명한 대로 무료 티어 공유 인스턴스는 CPU 경합으로 단발 측정에서 **20배 과대평가**가 나올 수 있다. 개선 전/후를 각각 한 번 재서 비교하면 그 노이즈를 "개선 효과"로 보고할 위험이 크다. **이번 설계의 핵심은 그 오독을 구조적으로 막는 것이다.**

## 2. 측정 대상과 가설

| 실험 | 개선 | 가설 | 측정 가능성 |
|---|---|---|---|
| **A** | P0-2 랭킹 view 캐시(`unstable_cache`) | `/predictions` p95가 캐시 히트 비용으로 떨어진다 | 높음 |
| **B** | P0-3·P1-4·P1-5 집계를 서버로 이동 | `/polls/{id}` p95 하락 + 응답 크기 감소 | 높음 |
| **C** | P1-7 `getUser` 중복 제거 | 왕복 수 감소 | **낮음 — 종단 지연에 안 나타날 수 있음** |

### 실험 C를 지연으로 재지 않는 이유

중복 `getUser()` 호출은 이미 `Promise.all`로 병렬이다. 왕복이 3회에서 1회로 줄어도 **가장 긴 하나가 그대로 남으므로 p95는 거의 안 움직인다.** 지연으로 재면 "개선 효과 없음"이라는 잘못된 결론이 나온다.

→ C는 k6 대상에서 제외하고 **호출 횟수**로 검증한다: Supabase Dashboard의 Auth 요청 수, 또는 개선 전/후 같은 시나리오를 돌린 뒤 Auth 로그 건수 비교. 지표가 다르므로 A/B 표에 섞지 않는다.

## 3. 가장 중요한 설계 판단 — 데이터 규모를 2단계로 나눈다

`20260824_백엔드_성능개선_점검.md` P2-1이 확인한 대로 prod는 현재 **50행대**다. 이 규모에서 A/B 차이를 재면 **개선 전후가 모두 노이즈에 묻혀 "차이 없음"이 나온다.** 그건 개선이 무효라는 뜻이 아니라 **측정이 무의미하다**는 뜻인데, 보고서에는 전자로 읽힌다.

그래서 두 규모에서 각각 잰다. 둘 다 필요하다.

| 규모 | 데이터 | 답하는 질문 |
|---|---|---|
| **S (현재)** | prod 실측 수준 (~50행) | "지금 이 수정을 해야 하나?" → 차이 없음이 **정답**이고, 그렇게 보고한다 |
| **L (성장)** | 1차 시드 수준 (표 10만, 예측 다수) | "성장하면 효과가 있나?" → 여기서 차이가 나야 수정이 정당화된다 |

1차 측정(상세 p95 290.75ms)도 prod 규모가 아니라 10만 표 시드에서 나온 값이다. 즉 L 규모는 이 리포의 기존 관행과 같고, S 규모를 추가하는 것이 이번 설계의 보강점이다.

**S에서 차이가 없고 L에서만 차이가 난다** — 이게 예상 결과이며, 그 자체가 "지금은 P0-2만 하고 나머지는 임계에서" 라는 결론의 근거가 된다.

## 4. 노이즈 통제 — A/B/A/B 인터리브

**하지 말 것**: 개선 전을 3회 연속 측정 → 코드 수정 → 개선 후를 3회 연속 측정.
공유 인스턴스의 CPU 경합은 시간 상관이 있어서, 측정 순서가 결과에 섞인다.

**할 것**: 로컬에 서버 2개를 동시에 띄우고 번갈아 측정한다.

```
git worktree로 체크아웃 2개 (.next 디렉터리가 분리돼야 한다)
  before → main 커밋 그대로     → npm run build && PORT=3000 npm start
  after  → 개선 브랜치          → npm run build && PORT=3001 npm start

측정 순서: before → after → before → after → before → after
  (라운드 3회, 각 라운드 안에서 두 서버를 연속 측정)

보고값: 라운드별 p95의 중앙값 (median of medians)
```

Vercel preview 대신 포트 2개를 쓰는 것이므로 인터리브 자체는 **오히려 간단해진다.** 라운드마다 두 조건이 같은 시간대의 머신·Supabase 인스턴스 상태를 공유하므로 경합이 양쪽에 동등하게 실린다. 라운드 간 편차가 조건 간 차이보다 크면 → **개선 효과를 주장할 수 없다**(6장 판정 기준).

주의 3가지:

- **`npm run dev`로 재지 말 것.** 반드시 `npm run build && npm start`. dev 모드는 요청마다 컴파일이 섞여 측정이 무의미하다.
- **같은 디렉터리에서 두 번 빌드하면 안 된다.** `.next`가 덮어써진다 → `git worktree`로 체크아웃을 분리한다.
- **실 Supabase 모드로 빌드했는지 확인한다.** `.env.local`이 없으면 `IS_MOCK = true`가 되어 DB를 아예 안 친다. 게다가 `getFixtureWeeks`/`getPollList`는 `unstable_cache` 안에 `IS_MOCK` 분기가 들어가 `.next/cache`가 모드 간에 오염된다(가이드 문서의 기존 함정). 측정 전 `rm -rf .next/cache`로 시작한다.

부하를 걸지 않는 쪽 서버는 유휴 상태라 CPU를 거의 쓰지 않으므로, 2개를 동시에 띄워두는 것 자체는 문제가 되지 않는다.

### 부하 수준을 1차보다 낮춘다 — 이게 로컬 전용 설계의 핵심 변경

1차 스크립트의 `measure` scenario는 VU를 100까지 올린다. **로컬 A/B에서는 그러면 안 된다.** k6와 Next.js가 같은 머신에 있으므로, 부하를 올리면 측정되는 값이 "개선 효과"가 아니라 "내 노트북의 CPU 경합"이 된다. 1차 3.3이 이미 `Insufficient VUs, reached 500 active VUs` 경고와 함께 그 한계를 기록했다.

이번 질문은 "이 수정이 요청 하나를 더 빠르게 처리하나"이므로 **동시성은 통제 변수로 낮게 고정**한다.

`MODE=ab`로 구현했다(반영 완료). 기존 `MODE=latency`는 **손대지 않았다** — 1차(8/21) 수치와 직접 비교 가능한 조건은 그것뿐이라, A/B용 저부하 시나리오로 덮어쓰면 기존 베이스라인과 나란히 놓을 수 없다.

```js
// MODE=ab — 로컬 A/B 전용 scenario. VU 램프 대신 낮은 고정 도착률
const ab = {
  warmup,                                    // 기존 워밍업 그대로 재사용
  measure: {
    executor: 'constant-arrival-rate',
    startTime: '30s',                        // 워밍업 종료 시점
    rate: Number(__ENV.RATE || 5),           // 5 iter/s ≈ 20 req/s (endpoint 4개)
    timeUnit: '1s',
    duration: __ENV.DURATION || '3m',        // 표본 약 900 iteration
    preAllocatedVUs: 20, maxVUs: 50,
    tags: { phase: 'measure' },
    exec: 'browseNoSleep',
  },
};
```

`RATE`·`DURATION`을 env로 뺀 이유는 바로 아래 `dropped_iterations` 재측정 때문이다 — 스크립트를 고치지 않고 `-e RATE=3`으로 낮춰 다시 잰다.

`ramping-vus`(VU 수 통제)가 아니라 `constant-arrival-rate`(도착률 통제)를 쓰는 이유: 서버가 느려져도 도착률이 유지되어 두 조건에 **같은 부하**가 들어간다. VU 통제는 서버가 느리면 도착률이 저절로 떨어져 조건 간 부하가 달라진다.

실행 중 `dropped_iterations`가 0이 아니면 그 라운드는 **머신이 부하를 못 따라간 것**이므로 폐기하고 `rate`를 낮춰 다시 잰다.

- **포화점 측정은 하지 않는다.** 로컬에서 포화점은 서버 용량이 아니라 노트북 CPU를 재는 것이다. 1차 3장 수치를 그대로 참조한다.
- 워밍업 scenario(기존 스크립트에 이미 있음)는 유지한다 — JIT·커넥션·캐시 채우기를 흡수한다.

## 5. 실행 절차

### 5.1 시드

**L 규모** — 기존 시드 재사용 + 예측 데이터 추가.

```
scripts/seed-load-test.sql        (기존) 유저 10만 + 표 10만  → 실험 B용
scripts/seed-load-test-polls.sql  (기존) 목록용 poll 다수
scripts/seed-load-test-predict.sql (신규 작성 필요)            → 실험 A용
```

신규 시드가 채워야 하는 것 — `week_leaderboard`는 `prediction_results`를 경유하고 그 view는 **`f.finished` 경기만** 담으므로, 아래가 다 있어야 랭킹 view에 행이 생긴다.

| 테이블 | 필요 조건 |
|---|---|
| `fixtures` | `finished = true`, `home_score`/`away_score` 채움, 12주 이상 분포 |
| `predictions` | 경기당 참가자 다수 (경기 × 사용자) |
| `fixture_player_ratings` | 경기별 픽 대상 선수 평점 — 없으면 픽 점수가 전부 0이 되어 계산 부하가 왜곡된다 |

주의: `predictions`의 insert RLS는 `kickoff_at > now()`를 요구하지만 종료 경기를 시드해야 한다. **psql/service-role로 넣어 RLS를 우회한다**(정책 자체를 건드리지 말 것 — 1차 5장의 drift 사고 재발 원인이다).

**S 규모** — 시드 없이 prod 스냅샷 복제 또는 시드 테이블 truncate 후 측정.

### 5.2 측정 대상 엔드포인트

`endpoint` 태그로 분리한다. 1차 2.1에서 캐시된 목록과 비캐시 상세를 합치면 80배 차이가 희석된다는 게 이미 증명됐다.

| 태그 | 경로 | 실험 | 캐시 상태(개선 전) |
|---|---|---|---|
| `list` | `/polls` | B(대조) | `unstable_cache` 30s |
| `detail` | `/polls/{POLL_ID}` | **B(핵심)** | 없음 |
| `predict-list` | `/predictions` | **A(핵심)** | 없음(시즌 랭킹) |
| `predict-week` | `/predictions/{WEEK_KEY}` | **A(핵심)** | 없음(주차 랭킹) |

전부 **비로그인 GET**으로 잰다. 랭킹은 참여 여부와 무관하게 공개(`predictions: public read`)이므로 인증 없이 같은 view 부하가 발생한다. 인증 경로는 이번 범위 밖(1차 한계와 동일).

### 5.3 스크립트 변경

**반영 완료.** 기존 `scripts/k6-load-test.js`에 예측 엔드포인트와 시나리오 선택만 추가했다. 구조와 기존 두 모드(`latency`/`saturation`)는 그대로다.

```js
// 추가 env
const WEEK_KEY = __ENV.WEEK_KEY || '2026-33';
const SUITE = __ENV.SUITE || 'all';   // polls | predict | all

const POLL_ENDPOINTS = ['list', 'detail'];
const PREDICT_ENDPOINTS = ['predict-list', 'predict-week'];
const endpoints = SUITE === 'polls' ? POLL_ENDPOINTS
  : SUITE === 'predict' ? PREDICT_ENDPOINTS
  : POLL_ENDPOINTS.concat(PREDICT_ENDPOINTS);

function get(path, endpoint) {
  const res = http.get(`${BASE_URL}${path}`, { tags: { endpoint } });
  check(res, { [`${endpoint} status 200`]: (r) => r.status === 200 });
}

function hit() {
  if (SUITE !== 'predict') {
    get('/polls', 'list');
    get(`/polls/${POLL_ID}`, 'detail');
  }
  if (SUITE !== 'polls') {
    get('/predictions', 'predict-list');
    get(`/predictions/${WEEK_KEY}`, 'predict-week');
  }
}
```

라우트는 `frontend/src/app/predictions/page.tsx` / `[weekKey]/page.tsx`로 존재를 확인했다.

`thresholds`는 하드코딩하지 않고 위 `endpoints` 배열에서 파생시켰다 — 1차 스크립트 주석의 경고(**데이터가 0건인 임계값도 k6는 `✓`로 출력한다**)를 주의사항이 아니라 구조로 막기 위해서다. `SUITE=predict`면 `list`/`detail` 임계값은 **애초에 생성되지 않는다.** `saturation` 모드에도 같은 방식을 적용했다(기존엔 `detail`만 걸려 있었다).

측정은 `MODE=ab`만 쓴다(4장: 포화 측정 제외). 1차 베이스라인을 다시 떠야 할 때만 `MODE=latency`를 쓴다.

### 5.4 한 라운드 실행

```bash
# 라운드 R, 조건 before (포트 3000)
k6 run -e MODE=ab -e BASE_URL=http://localhost:3000 -e SUITE=all -e POLL_ID=... -e WEEK_KEY=... \
       --summary-export=results/R{n}-before.json scripts/k6-load-test.js

# 라운드 R, 조건 after (포트 3001, 즉시 연속 실행)
k6 run -e MODE=ab -e BASE_URL=http://localhost:3001 -e SUITE=all -e POLL_ID=... -e WEEK_KEY=... \
       --summary-export=results/R{n}-after.json scripts/k6-load-test.js
```

`-e MODE=ab`를 빠뜨리면 기본값 `latency`(VU 100 램프)로 돌아가 4장이 금지한 고부하 측정이 된다. 커맨드에서 가장 틀리기 쉬운 부분이다.

라운드 3회 × 규모 2단계 = **12회 실행**. 워밍업 30s + measure 3m = 1회 약 3.5분이므로 실행 시간 약 45분.

측정 중 다른 작업(빌드, 브라우저, 에디터 인덱싱)을 돌리지 않는다 — 로컬 측정에서는 이게 가장 큰 노이즈원이다. 라운드 간 편차가 크게 나오면 대개 이것 때문이다.

### 5.5 캐시 경계 처리 — 실험 A에서 반드시 필요

실험 A의 개선안이 **캐시 추가**이므로, 개선 후 측정이 캐시 히트만 잡으면 "무한히 빨라졌다"는 무의미한 결과가 나온다. 두 값을 나눠 보고한다.

| 값 | 재는 방법 | 의미 |
|---|---|---|
| **캐시 히트 지연** | 워밍업 후 정상 measure 구간 | 실사용자 대다수가 겪는 값 |
| **캐시 미스 지연** | `revalidate` 직후 첫 요청 (배포 직후 첫 히트 또는 60s 대기 후 단발 요청) | view 재계산 비용 — 개선 전과 **같아야 정상** |

개선 전은 캐시가 없으므로 모든 요청이 미스다. 즉 **정직한 비교는 "개선 전 전체" vs "개선 후 히트+미스 혼합"**이고, 미스 지연이 개선 전과 같다는 것까지 같이 보고해야 "캐시로 가렸을 뿐 쿼리는 그대로"라는 사실이 드러난다.

## 6. 판정 기준 (사전 확정 — 측정 후 조정 금지)

측정을 보고 기준을 정하면 원하는 결론이 나온다. 먼저 못 박는다.

| 판정 | 조건 |
|---|---|
| **개선 확인** | 라운드 3회 **모두**에서 after p95 < before p95, 그리고 (before − after) 중앙값이 **라운드 간 편차 폭보다 크다** |
| **판정 불가** | 라운드 간 편차가 조건 간 차이보다 큼 → "측정 노이즈에 묻힘"으로 보고. 개선 효과를 주장하지 않는다 |
| **개선 없음** | after가 before보다 느린 라운드가 1회 이상 |

보조 확인:

- **p95와 중앙값을 같이 본다.** 1차 2.2에서 중앙값은 +2.7ms인데 p95는 2배가 된 사례가 있었다. 평균 단독 보고 금지.
- **응답 크기**(`data_received`) — 실험 B는 1,000행(약 56KB) 페이로드가 사라지는 것이 핵심이므로, 지연보다 이쪽이 먼저 움직인다.
- **에러율** — 개선 후 0%가 아니면 지연 수치는 무효다.

### 예상 결과 (미리 적어두고 맞는지 확인)

| 실험 | S 규모 | L 규모 |
|---|---|---|
| A (랭킹 캐시) | 판정 불가(차이 없음) | 개선 확인 — 캐시 히트 경로 |
| B (집계 이동) | 판정 불가 | 개선 확인 — 지연 + 응답 크기 |
