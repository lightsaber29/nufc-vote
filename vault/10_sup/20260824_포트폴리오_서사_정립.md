## 2. 왜 성능 개선 수치가 안 나오나

prod 실데이터 실측 (1차 4.5, 성능개선 점검 P2-1):

| 대상                | 실제 규모     |
| ----------------- | --------- |
| poll별 최대 표 수      | 1,000건 미만 |
| poll별 최대 평점 수     | **52건**   |
| `rating_votes` 전체 | **52건**   |

**50행짜리 테이블에서는 무엇을 어떻게 짜도 빠르다.** 인덱스를 붙여도, 집계를 DB로 내려도, 캐시를 붙여도 차이가 측정 한계 아래다. 비교실험 설계서 3장이 스스로 그렇게 예측하고 있다 — S 규모에서는 전 항목 "판정 불가".

그러니 부하 테스트가 성능 문제를 못 찾은 건 **테스트가 부실해서가 아니라 문제가 없어서**다. 그리고 이 규모에서 부하를 걸면 대신 나오는 게 있다 — **작을 땐 맞는데 커지면 틀리는 전제들**이다. 실제로 그것만 나왔다.

> **이 사실 자체가 산출물이다.** "예상한 병목이 실측 결과 병목이 아니었고, 계획서 2순위 개선은 실효가 없어 폐기했다"는 것은 측정하지 않으면 쓸 수 없는 문장이다.

## 3. 목적 재정의 — 왜 "디버깅"이 아니라 "규모 가정 검증"인가

### 3.1 디버깅은 목적이 될 수 없다

목적을 정하는 실질적 이유는 방향 설정이 아니라 **종료 조건 설정**이다. 성능 테스트는 시나리오·규모·경로를 무한히 늘릴 수 있어서, 멈추는 근거가 목적 달성뿐이다.

| 목적             | 종료 조건               |
| -------------- | ------------------- |
| "p95 500ms 이하" | 달성하면 끝              |
| "동시 1,000명 확인" | 확인하면 끝              |
| **"버그 찾기"**    | **없음. 버그는 항상 더 있다** |

성공/실패를 정의할 수 없으면 목적이 아니라 활동이다.

### 3.2 애초에 이번에 한 건 디버깅이 아니었다

디버깅은 **증상에서 출발**한다. 이번엔 증상이 없었다 — 아무도 불평하지 않았고 화면은 멀쩡했다. 증상 없이 조건을 바꿔 찾아낸 것이므로 **탐색**이다.

덧붙이면, 버그 찾기가 목적이었다면 부하 테스트는 비효율적인 도구였다. 1,000행 캡은 `select()` 전수 grep으로 30분이면 나왔다 (7장 참조).

### 3.3 "규모 가정 검증"은 종료 조건이 있다

> 주요 조회 경로가 암묵적으로 전제하는 규모·시간·환경 가정을 목록화하고, 실제로 그 밖의 조건을 만들어 검증한다.

가정 목록이 유한하므로 끝이 있다. 1차 문서 7장의 "1,000행 캡 전수 조사 미완"이 그대로 이 목적의 잔여 작업이 된다.

발견 3건이 이 프레임에 그대로 들어맞는다:

| 발견 | 깨진 암묵적 가정 |
|---|---|
| 1,000행 캡 | "`select()`는 전부 가져온다" — 행 수 가정 |
| `vote_count` stale | "정적 페이지는 알아서 갱신된다" — 시간 가정 |
| prod drift | "마이그레이션이 곧 스키마다" — 환경 가정 |

## 4. 서사의 중심 — 발견 4건이 전부 "조용한 실패"다

3장의 프레임은 발견 3건만 설명한다. 1차 3.1(큐잉 붕괴)은 규모 가정이 깨진 게 아니라 부하가 걸린 것이라 빠진다.

그런데 4건을 증상 쪽에서 보면 **하나로 묶인다.**

| 발견 | 겉보기 | 실제 |
|---|---|---|
| 1,000행 캡 | HTTP 200, 정상 배열 | 집계가 틀림 |
| prod drift | 정상 화면 | 전부 0표로 표시 |
| `vote_count` stale | 정상 숫자 | 빌드 시점에 정지 |
| 포화 시 큐잉 | **에러율 0%** | 사용자는 20초 대기 |

**넷 다 에러가 나지 않는다.** 로그도 없고 알람도 안 울리고 화면은 멀쩡하다.

### 그래서 이름을 두 층으로 나눈다

하나의 이름으로 목적과 결과를 다 담으려니 안 된다. 원래 둘은 다른 것이다.

| 층 | 이름 | 역할 |
|---|---|---|
| **작업 목적** | 규모 가정 검증 | 언제 그만둘지 정한다 (종료 조건 있음) |
| **결과 제목** | **조용한 실패** | 남에게 설명할 때 쓴다 (4건 전부 커버) |

문서·발표에서의 한 줄:

> **목적**: 코드가 전제하는 규모 가정을 실제 규모를 만들어 검증한다
> **결과**: 4건을 찾았고, **전부 에러를 내지 않는 결함**이었다 — 그래서 지금까지 아무도 몰랐다

### 5.2 직군을 백엔드로 확정하는 이유

전체점검 5장 기준 **프론트엔드 원페이저의 범위 5개가 전부 미착수**다(Pretendard 서브셋, fetchpriority, Storage cacheControl, PC 반응형, 번들 측정). 반면 백엔드 축은 베이스라인·포화점·정산 배치·테스트 103건이 이미 있다.

둘 다 하려다 둘 다 얕아지는 것이 가장 나쁘다. **백엔드로 확정하고 프론트 항목은 "범위 밖"으로 명시**하는 편이 낫다.

### 5.3 성능 20점을 어떻게 채우나

배점표의 "상위로 보이려면"은 **"병목을 찾아 개선 전후 수치를 제시"**를 요구한다. 개선할 성능이 없다는 게 우리 결론이므로 정면 충돌한다. 셋으로 나눠 대응한다.

1. **개선 전후 수치 1건은 확보한다** — 실험 A(랭킹 view 캐시). L 규모에서 재면 차이가 난다. 이것만 있으면 "제시했다"가 성립한다
2. **"안 한 판단"을 산출물로 제시한다** — 인덱스 9개와 정렬 인덱스를 **측정 후 폐기**했다. 근거 있는 미실행은 근거 없는 실행보다 낫고, 그걸 설명할 수 있는 지원자는 드물다
3. **포화 특성을 성능 축의 대표 성과로 앞세운다** — 1차 3.1. p95 143ms에서 4,370ms(약 30배)로 무너지는데 에러율은 0%다. 이건 부하 테스트로만 알 수 있는 정보다

## 6. 남은 작업 — 우선순위 재배치

### 6.1 최우선: 관측성 구현 (신규)

1차 3.1이 이렇게 끝난다:

> 에러율·5xx만 모니터링하면 이 상태를 탐지할 수 없다. 사용자는 20초를 기다리는데 알람은 울리지 않는다. **요청 로깅과 지연 기반 알람이 필요하다.**

배점표의 백엔드 "채용에서 보는 것"에 **관측성**이 명시돼 있고, 플래그십 요건에도 **요청 로깅**이 들어 있다. 그런데 지금 없다.

**이걸 구현하면 서사가 닫힌다** — 부하 테스트로 사각지대를 실측 → 그걸 메우는 관측성을 구현. 발견과 조치가 한 쌍이 되고, 성능 개선 수치 없이도 성능 축이 성립한다.

지금 가장 투자 대비 회수가 큰 작업이라고 본다.

### 6.2 그다음: 발견한 것 실제로 고치기

발견만 하고 안 고치면 "찾을 줄은 아는데 못 고친다"로 읽힌다.

| 작업 | 비용 | 문서 |
|---|---|---|
| `/polls`에 `revalidate = 30` | 1줄 | 렌더링 점검 1.3 |
| `loading.tsx` 3개 | 파일 3개 | 렌더링 점검 2장 |
| 1,000행 캡 3곳 RPC 전환 | 중간 | 1차 4.4 |
| 랭킹 `isMe` 분리 후 캐시 | 함수 2개 | 렌더링 점검 3장 |
| prod에 drift 마이그레이션 적용 | 미결정 | 1차 5.3 |

### 6.3 축소: k6 비교실험

설계서 원안은 12회 실행 45분이고, 예상 결과가 이미 "S 규모 전부 판정 불가"다. 아는 답을 확인하는 데 쓰는 시간이다.

| | 원안 | 제안 |
|---|---|---|
| 실험 A (랭킹 캐시) | S·L 각 3라운드 | **L만 3라운드** — 유일하게 로컬 편향 없고 실체 있음 |
| 실험 B (집계 이동) | S·L 각 3라운드 | **측정 없이 정확성으로 종결** — 1차 4.4가 "느려서가 아니라 틀려서"로 결론냄 |
| 실험 C (getUser) | Auth 호출 수 | 실험 A와 **같은 수정**이므로 통합 (렌더링 점검 3장) |
| 합계 | 12회 / 45분 | **6회 / 20분** |

### 6.4 검토 필요: CI

재현성 15점 항목이고 전체점검 1d에 "미해결"로 있다. 테스트 103건이 이미 있으므로 GitHub Actions 워크플로 하나면 된다. 비용 대비 점수 효율이 높다.

## 7. 도구 재배치 — 앞으로는 k6가 아니다

발견 4건을 메커니즘으로 분해하면 확인 방법이 갈린다.

| 메커니즘 | 확인 도구 | 리포 실측 |
|---|---|---|
| ① 성공 코드를 반환하는 절단 | grep + 판정 | `select()` 28곳 중 `limit`/`range` **5곳뿐** → 23곳 미확인 |
| ② 에러를 삼키고 기본값 반환 | 코드 리뷰 | `if (error` 38곳, 빈 기본값 반환 23곳 |
| ③ 무효화 누락 | 액션 × 캐시 매트릭스 | 액션 12파일 전수 대조 미실시 |
| ④ 환경 간 차이 | `pg_policies` 항목 단위 대조 | 1차 5.4가 방법 확정 |
| ⑤ 자원 고갈이 지연으로만 발현 | **k6** | 1차 3.1에서 확인 완료 |

**k6가 실제로 필요한 건 ⑤ 하나뿐이고, 그건 이미 했다.** 나머지 ①~④는 정적 분석으로 훨씬 싸게 잡힌다.

부하 테스트가 헛수고였다는 뜻은 아니다 — ①을 발견하게 만든 계기가 10만 표 시드였다. 다만 **발견 이후에는 도구를 바꾸는 것이 맞다.** 남은 23곳을 k6로 찾을 이유가 없다.

### 체크리스트를 돌리자마자 걸린 후보 1건

`lib/queries/fixtures.ts:12` — `getFixtureWeeksUncached`가 함수 안에서 `Date.now()`를 계산해 주차 상태·`locked` 판정에 쓰는데, 그 함수 전체가 `unstable_cache(revalidate: 300)`로 감싸져 있다. **`now`가 캐시에 최대 5분간 얼어붙는다.**

영향 지점: `app/predictions/[weekKey]/page.tsx:20`의 `notFound()` 판정, `submittableMatches(week)`의 제출 가능 경기 결정.

킥오프 직전 5분 창에서 화면은 제출 가능하다고 표시하는데 실제 제출은 RLS(`kickoff_at > now()`)에 막힐 수 있다. 전형적인 조용한 실패이고, **경기 시작 직전이 정확히 사용자가 몰리는 시간대**다.

미확정 — `lib/predictions/week.ts` 로직 확인 후 판정 필요.

## 9. 하지 말 것

- **"처음부터 규모 가정 검증을 노렸다"고 쓰지 않는다.** 계획서(8/20)·1차 결과(8/21)·2차 설계(8/24)가 다 남아 있어 대조하면 드러난다. 사후 정립 자체는 흠이 아니지만 은폐는 흠이다
- **실체보다 큰 이름을 붙이지 않는다.** "조용한 실패"는 실체보다 작게 들리는데 내용이 그걸 넘어서는 쪽이라 안전하다
